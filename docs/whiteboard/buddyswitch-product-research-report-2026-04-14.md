## 1. 报告说明

本文档是一份基于当前仓库实现、文档结构和产品机制整理的内部产品调研报告，用于回答以下问题：

1. BuddySwitch 到底是什么产品。
2. 它解决的是哪一类用户和团队的问题。
3. 它相较于普通 AI 聊天、Agent 工具编排、任务管理工具的差异在哪里。
4. 它现阶段最适合切入什么场景，未来又可能扩展到哪里。

需要明确的是：

- 本报告主要基于 BuddySwitch 当前代码仓库与产品结构进行归纳。
- 它更接近“产品判断 + 形态分析 + 市场映射”的 desk research。
- 它不是外部市场访谈报告，也不包含第三方行业数据库或付费研究结论。

## 2. 结论先行

BuddySwitch 可以定义为：

```text
一个运行在 Codex CLI 会话中的、多角色 AI 协作操作层。
```

它并不是单纯的聊天机器人，也不是传统的 workflow engine，而是把一组明确分工的 AI buddy 组织成一个可切换、可追踪、可接力、可持久化的工作环境。

当前最准确的产品定位是：

```text
BuddySwitch = 面向产品研发流程的 AI 协作环境层
+ 角色路由
+ 结构化任务对象
+ 结构化产物对象
+ 可持续 run 审计
```

它的核心价值不在于“回答一次问题”，而在于：

- 把跨角色协作从临时对话升级为持续工作流。
- 把 AI 输出从散乱文本升级为可管理对象。
- 把 handoff 从口头描述升级为可追踪状态迁移。

如果用一句更偏产品化的话来概括：

```text
BuddySwitch 想做的，不是“一个更会回答问题的 AI”，
而是“一个能让 AI 像团队一样分工协作的工作环境”。
```

## 3. 产品定义

## 3.1 产品是什么

从当前仓库看，BuddySwitch 由四层组成：

1. 一套统一交互协议  
   用户通过 `switch <buddy>(<task-id>) -> <track-id>: <demand>` 发起工作指令。

2. 一套角色化执行单元  
   当前角色包括 `market`、`pm`、`design`、`dev`、`test`，每个 buddy 只负责自己权限范围内的工作。

3. 一套结构化状态模型  
   核心对象包括：
   - track
   - task
   - artifact
   - run

4. 一套 resolve / execute / persist 运行机制  
   它把一次用户需求转成：
   - 技能选择
   - 上下文解析
   - 结构化结果
   - 落盘审计

因此 BuddySwitch 的产品本质，不是单点能力，而是一种运行时环境。

## 3.2 它不是什么

为了避免定位模糊，也需要明确 BuddySwitch 不是什么：

- 不是普通聊天产品  
  它不是以对话体验本身为核心卖点，而是以工作组织能力为核心。

- 不是通用任务管理软件  
  它不是人类团队手工维护的 Jira / Notion 替代品，而是 AI 执行过程的状态层。

- 不是纯 Agent 框架  
  它没有把重点放在 agent 自主探索，而是强调显式切换、显式边界、显式持久化。

- 不是一次性 prompt 模板集合  
  它不是“提示词仓库”，而是有对象模型、路由规则和执行收据的系统。

## 4. 用户问题与需求洞察

## 4.1 当前 AI 协作的典型问题

从 BuddySwitch 的设计反推，它试图解决的核心问题主要有五类。

### 1. AI 工作无法稳定分工

在普通对话式 AI 使用中，用户经常需要手动提示：

- 现在请你扮演 PM
- 现在请你切到设计师视角
- 现在请继续之前的开发任务

这种模式的问题是：

- 角色切换不稳定
- 上下文边界不清楚
- 输出格式难统一
- 后续难追责和复用

BuddySwitch 用 buddy 和 skill 显式定义了角色边界，降低“一个模型扮演所有人”的混乱感。

### 2. 多轮工作难以持续接力

传统聊天中，一次输出结束后，后续继续工作非常依赖上下文窗口记忆。只要 session 变长、重启、切模型，协作链路就容易断掉。

BuddySwitch 引入 task、track、artifact、run，使每次执行都能被持久化并挂回到可追踪对象上，从而让“继续上次工作”这件事变得稳定。

### 3. 产出很难被管理

普通 AI 输出常见的问题：

- 文本很多，但对象关系弱
- 结论有了，但缺版本语义
- 很难知道什么是当前有效版本
- 很难知道下一步该由谁接手

BuddySwitch 通过 artifact slot、task 状态、reference switches、recommended switch 等机制，把“结果”从自由文本提升成“可衔接的工作对象”。

### 4. 团队协作缺少明确 handoff

在真实产品研发中，市场、产品、设计、开发、测试往往是接力式关系。普通 Agent 系统大多强调 autonomous loops，但对 handoff 的治理较弱。

BuddySwitch 反而把 handoff 作为一等公民：

- 谁可以创建或推进 track
- 谁只读 track
- 谁基于 task 产出 artifact
- 完成后推荐下一条 `switch` 指令

这使它更像“AI 团队协作协议”，而不是“单 Agent 自动执行器”。

### 5. 缺乏审计与可回放能力

企业或团队如果要长期使用 AI，需要回答几个问题：

- 这条结果是谁产出的。
- 它基于什么上下文。
- 它属于哪个任务。
- 它是否已经被后续覆盖。
- 如果出现问题，能否追溯当时的 run。

BuddySwitch 的 run audit 机制明显是为这个问题而设计。

## 4.2 隐含用户需求

从产品结构判断，BuddySwitch 面向的不是“想偶尔问 AI 一个问题”的轻度用户，而是有以下需求的人群：

- 需要长期用 AI 协助推进产品研发的人
- 需要让不同 AI 角色协同工作的人
- 需要保留工作轨迹的人
- 需要把 AI 输出纳入项目过程的人

换句话说，它瞄准的是“持续协作需求”，不是“即时问答需求”。

## 5. 目标用户与典型场景

## 5.1 核心目标用户

### 1. AI-native 的产品负责人

这类用户需要快速在市场、PRD、设计、开发、测试之间切换，并希望 AI 不只是出点子，而是真正成为一个分工明确的执行网络。

BuddySwitch 对这类用户的价值在于：

- 不用反复重建上下文
- 不用每轮重新指定角色
- 可以把每一步产出沉淀为任务与产物

### 2. 小团队创始人或独立开发者

一个 1 到 5 人团队通常缺的是完整职能带宽，而不是单点能力。创始人往往同时承担市场、产品、设计、开发多个职责。

BuddySwitch 提供的是一种“低人力条件下的多角色 AI 协作面板”，适合：

- 需求验证
- MVP 定义
- 设计拆解
- 开发推进
- 冒烟验收

### 3. 内部使用 AI 的产品工程团队

当团队希望把 AI 纳入正式流程，而不是把 AI 当成私人草稿工具时，BuddySwitch 的结构化对象模型就会变得有吸引力，因为它更容易接入：

- 审批与 review
- 变更记录
- 内部审计
- 团队 handoff

## 5.2 最适合的初始场景

根据当前 buddy 设计，BuddySwitch 最适合切入的场景不是所有知识工作，而是“产品研发闭环”。

比较适合的场景包括：

- 新产品机会扫描
- 某条产品 track 的持续推进
- 从 PRD 到 IA spec 再到开发与测试的顺序流转
- 对同一个产品能力进行多轮结构化迭代

不太适合作为第一切入点的场景包括：

- 完全开放式的研究咨询
- 强依赖非结构化长文创作的内容团队
- 复杂多人审批流企业系统
- 高度依赖 GUI 操作而非 CLI 的大众用户

## 6. 产品机制分析

## 6.1 统一指令协议

BuddySwitch 的一个强设计点，是使用统一的 `switch` 指令完成：

- 角色声明
- 任务引用
- track 归属
- 用户需求表达

这带来几个产品好处：

- 学习成本相对低
- 使用方式一致
- 便于复制、重放和审计
- 更容易作为 host 环境的标准输入协议

相比随意自然语言提示，这种协议化输入更适合长期系统化使用。

## 6.2 显式角色边界

当前 manifest 中每个 buddy 都有：

- `scope`
- `skills`
- `permissions`

这意味着 BuddySwitch 的产品哲学是：

```text
先定义谁负责什么，
再定义他能用什么技能，
最后定义他能写哪些对象。
```

这种结构对于产品研发尤其重要，因为它天然贴合现实团队分工，而不是让一个通用 agent 模糊承担所有责任。

## 6.3 结构化对象优于自由文本

BuddySwitch 把工作沉淀到四类对象：

- track: 持续推进的主题或工作线
- task: 某次执行或子任务的工作单元
- artifact: 当前产出的结构化结果
- run: 执行审计记录

这比单纯保留聊天记录更有产品意义，因为它让系统能回答：

- 当前工作线是什么
- 当前任务属于哪条线
- 当前有效产物是什么
- 最近几次执行发生了什么

这为后续做：

- 面板化展示
- 历史比较
- 自动汇总
- 结果推荐

提供了天然基础。

## 6.4 `resolve -> execute -> persist` 分层

这是 BuddySwitch 最值得保留的底层产品逻辑之一。

- `resolve` 负责解析请求和确定可执行候选
- host session 负责真正执行技能
- `persist` 负责校验和落盘

这个设计的价值在于把“理解需求”“生成内容”“写入系统”三件事拆开了。  
对产品而言，这意味着：

- 更容易加治理
- 更容易做回放
- 更容易限制错误写入
- 更容易在未来支持更多 host 或 UI

## 6.5 收据式输出

BuddySwitch 规定终端输出必须包含：

- Receipt
- Commands
- Summary

这看似只是输出格式约束，实际是一个很强的产品决策。

因为它把一次 AI 执行从“回答了一段话”变成：

- 我做了什么
- 写到了哪里
- 生成了什么对象
- 下一步建议怎么继续

这种收据式体验，非常适合工具化产品，而不是聊天型产品。

## 7. 竞争与替代关系分析

BuddySwitch 当前不会直接与某一个单一产品完全重叠竞争，它更可能同时替代几类工具的局部功能。

## 7.1 替代对象一：普通 AI 聊天使用方式

替代逻辑：

- 过去：用户手动在一个长会话里不断切角色、补上下文、复述状态。
- BuddySwitch：用户通过 `switch` 指令直接进入明确角色和任务上下文。

相对优势：

- 更稳定的角色切换
- 更明确的状态管理
- 更容易继续上一次工作

相对短板：

- 灵活性不如自由聊天
- 初始学习成本更高
- 对用户的结构化表达要求更高

## 7.2 替代对象二：轻量 Agent orchestration

很多 Agent 产品重视“自动执行链”，但不重视工作对象的沉淀。

BuddySwitch 的差异点在于：

- 更重视角色边界
- 更重视对象化持久化
- 更重视 handoff
- 更适合产品研发流程

短板在于：

- 自动化闭环程度目前不算高
- 仍然较依赖 host session 的人工选择
- 生态工具广度暂时有限

## 7.3 替代对象三：项目管理与文档工具中的 AI 使用方式

许多团队会在 Notion、Linear、Jira 等工具里记录 AI 产出，但这些工具本身不是为 AI 执行状态设计的。

BuddySwitch 的优势在于：

- 它把 AI 运行作为第一类对象来设计
- 它把角色切换和产物沉淀串成一个连续机制

但它的劣势也很明显：

- 当前主要存在于 CLI 环境
- 团队协同界面能力仍弱
- 对非技术用户不够友好

## 8. 差异化优势

综合来看，BuddySwitch 当前最清晰的差异化，不是“模型更强”或“生成更好”，而是以下四点。

### 1. AI 团队化，而不是 AI 单体化

BuddySwitch 的产品核心不是一个万能 agent，而是一组有边界、有权限、有职责的 buddies。

### 2. 工作对象化，而不是聊天记录化

它沉淀的是 task、track、artifact、run，而不是零散消息。

### 3. handoff 原生化，而不是后补式

它从一开始就把“下一步该切给谁”纳入设计，而不是把多角色协作交给用户自己记忆。

### 4. 可审计与可回放

它天然更适合需要过程记录和后续复查的场景。

## 9. 产品风险与挑战

## 9.1 使用门槛风险

BuddySwitch 当前的交互方式偏框架化、工程化。对于没有 CLI 使用习惯的人而言，学习成本明显高于普通聊天产品。

风险在于：

- 用户理解不了 `task`、`track`、`artifact` 的区别
- 用户不愿记忆 `switch` 协议
- 用户把它当聊天框使用时，会感到拘束

## 9.2 场景聚焦风险

BuddySwitch 目前在产品研发场景里有很强的一致性，但如果试图过快扩到所有知识工作，角色体系和对象模型可能失焦。

风险表现为：

- 新 buddy 无限制增长
- skill catalog 迅速膨胀
- 不同场景需要完全不同对象模型

这会稀释产品主线。

## 9.3 自动化与可控性的平衡

BuddySwitch 当前偏向可控、可审计、可显式切换。这是优点，但也意味着“自动帮我跑完一切”的体验不强。

如果未来产品要增强自动化，核心挑战是：

- 自动化不能破坏角色边界
- 自动化不能破坏 run audit
- 自动化不能让用户失去对 handoff 的理解

## 9.4 价值感知风险

用户第一次接触时，最容易问的问题是：

```text
这跟我直接对 ChatGPT / Codex 说“你现在扮演 PM”有什么本质区别？
```

如果这个问题回答不清，BuddySwitch 的价值就会被误解成“多了一层语法糖”。

因此它必须在产品表达上突出：

- 持续协作
- 对象持久化
- 结构化 handoff
- 审计可回放

而不是只强调多角色。

## 10. 当前阶段的最佳产品定位

结合当前实现与风险，BuddySwitch 最适合的阶段性定位不是“大而全 AI 平台”，而是：

```text
面向 AI-native 产品研发团队的多角色协作环境。
```

这个定位有几个优点：

- 与现有 buddy 体系高度一致
- 与当前对象模型天然匹配
- 与 CLI 工作流用户更贴近
- 便于讲清“为什么需要 track / task / artifact / run”

进一步压缩后，也可以表述为：

```text
BuddySwitch 是一个让产品、设计、开发、测试型 AI 能像团队一样协同工作的环境层。
```

## 11. 建议的产品叙事

如果要对外表达 BuddySwitch，建议采用以下叙事顺序。

### 第一层：先讲用户问题

用户今天使用 AI 做产品工作时，最大问题不是“AI 不够聪明”，而是：

- 上下文断裂
- 角色混乱
- 结果无法持续接力
- 工作过程无法沉淀

### 第二层：再讲 BuddySwitch 的解决方案

BuddySwitch 用：

- 明确的 buddy 角色
- 统一的 `switch` 指令
- 结构化的 task / track / artifact / run
- 显式的推荐下一步命令

把产品研发流程变成一条可持续推进的 AI 协作链。

### 第三层：最后讲结果

最终带来的不是一次回答质量的提升，而是：

- 更稳定的多角色协作
- 更清楚的过程管理
- 更容易继续工作
- 更适合团队化与长期化使用

## 12. 产品路线判断

如果沿着当前方向继续推进，BuddySwitch 后续比较合理的演进路径大致有三步。

### 1. 先把产品研发主线打深

优先把现有 `market -> pm -> design -> dev -> test` 主线打磨完整，而不是过早扩展更多 buddy。

### 2. 强化可视化工作台

当前已有 Context Panel 的基础。后续最值得加强的是：

- 当前 track / task / artifact 的可视化关系
- 当前有效产物的版本理解
- 历史 run 的对比与筛选
- handoff 推荐的面板化呈现

### 3. 逐步增强协作自动化

在保持可审计的前提下，增加：

- 更强的默认继续逻辑
- 更清晰的 next buddy recommendation
- 更稳健的多步流程模板

但不宜过早走向完全黑盒自动执行。

## 13. 综合判断

BuddySwitch 当前是一个方向清晰、机制成熟度高于普通 prompt 工具、但仍处在早期产品塑形阶段的系统。

它已经具备较强的产品骨架：

- 有清晰输入协议
- 有明确角色边界
- 有结构化对象模型
- 有执行与落盘分层
- 有审计和接力能力

这意味着它不是一个概念原型，而是一个已经拥有明确产品哲学的工作环境雏形。

如果说普通 AI 产品解决的是“怎么回答得更像专家”，那么 BuddySwitch 解决的是另一个层级的问题：

```text
怎么让多个 AI 角色像一个产品团队那样持续协作。
```

这正是它最值得继续强化的产品主线。

## 14. 附：一句话版本

### 外部短介绍

BuddySwitch 是一个运行在 Codex CLI 中的多角色 AI 协作环境，让市场、产品、设计、开发、测试型 AI 可以基于统一协议分工执行，并把任务、产物和运行记录持续沉淀下来。

### 内部定位版本

BuddySwitch 不是单次问答工具，而是面向产品研发流程的 AI 协作操作层，重点解决角色切换、任务接力、结构化产物沉淀和 run 审计四个问题。
