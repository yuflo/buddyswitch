02 / Dynamic discovery

Find targets from the repository that exists now

The algorithm is stable even when every module name changes. It ranks live evidence and broadens only when the current boundary cannot be proven.

1Name the claimState the behavior, contract, or repository-wide outcome that verification must prove.
2Read and partition stateInspect modified and untracked facts; separate task-related changes from pre-existing unrelated worktree changes.
3Prefer changed testsNew or modified exact tests are the strongest candidates; deleted tests require surviving proof or an explicit coverage decision.
4Trace current referencesSearch current tests for changed public symbols, commands, schemas, outputs, and direct callers.
5Stop or resolveStop when the claim and direct boundaries are covered; otherwise ambiguity is an escalation signal.
6Batch safelyBatch targets compatible under the current runner and isolate targets the runner marks exclusive.

4. Relevant broad gateAdded only when shared architecture, resources, or unresolved boundaries require it.

03 / Escalation

Scope grows with the claim, not with anxiety

Click a state. Behavior changes use RED; pure refactors may establish baseline GREEN first. No state means “run everything just in case.”

Breadth labels, not mandatory runs: reuse valid evidence across transitions. MILESTONE and FINAL are entered only when the claim requires them.

Triggered only when executable state changes after a valid FINAL run. It returns to FINAL after exact and affected proof passes and the tree freezes again.

05 / Responsibility

Review does not erase verified work

These are responsibilities, not required agent counts. One actor may hold several roles; no role repeats a broad suite merely to demonstrate independence.

Implementer

Owns RED, GREEN, and affected proof.

  • Names the claim before the command.
  • Records exact evidence.
  • Escalates on changed boundaries.

Reviewer

Owns findings, not ritual reruns.

  • Checks evidence identity.
  • Runs finding-specific probes.
  • Does not default to broad suites.

Controller

Owns the final breadth claim.

  • Freezes executable state.
  • Runs full once at FINAL.
  • Reuses valid subordinate evidence.

Runner

Owns deterministic execution.

  • Validates explicit targets.
  • Enforces current resource constraints.
  • Reports cleanup and exit state.

06 / Skill priority

Keep generic discipline; specialize repository scope

The repository skill does not fork TDD or completion discipline. It supplies the missing BuddySwitch-specific definition of sufficient verification.

Existing guidanceRetained responsibilityBuddySwitch specialization
superpowers:test-driven-developmentBehavior changes start RED; the smallest implementation reaches GREEN.RED and GREEN use the exact target discovered from the current repository. “Other tests” means IMPACT scope, not automatic full.
superpowers:verification-before-completionNo passing or completion claim without observed command output.“Complete command” means complete for the stated claim. Repository full is reserved for FINAL.
superpowers:requesting-code-reviewReview inspects specification fit, quality, risk, and supplied evidence.Review alone preserves evidence. Reviewers run finding-specific probes instead of repeating broad suites.
superpowers:subagent-driven-developmentMay select an agent workflow when tasks are actually independent.The testing skill is actor-count neutral. It does not require implementer/reviewer/controller reruns for every task.
AGENTS.md verification contractPublishes the current focused/final commands and runner-owned constraints.The skill consumes this contract dynamically; it does not copy command semantics into feature-specific branches.
Repository rule wins on scope.When generic guidance says fresh or complete verification, freshness is determined by evidence identity and completeness is bounded by the current claim. Neither term means “run ./buddyswitch-test full now.”

08 / Design choice

Local deployment without lifecycle coupling

The selected option gains repository awareness through a narrow public contract, not through stored knowledge of product modules.

Rejected

Project snapshot skill

Efficient briefly, then progressively wrong.

  • Embeds module and test maps.
  • Requires feature-lifecycle edits.
  • Creates a second topology truth.
Selected

Stable repo-local protocol

Dynamic discovery behind a narrow verification contract.

  • Zero feature knowledge.
  • Claim-based scope escalation.
  • Evidence reuse with invalidation.
Deferred

Global orchestration framework

Potential extraction only after another repository proves the same stable pattern.

  • Would require adapter abstractions.
  • No second real use case yet.
  • Premature under SHARP.

09 / Maintenance boundary

Feature evolution must not edit the skill

The skill changes only when its public verification protocol changes. Everything else is current repository data discovered at use time.

Feature added or removedNO EDITDiscover changed tests and current references.
Module or test renamedNO EDITRead current paths and symbols instead of a map.
Test tree growsNO EDITRunner and repository facts expose current targets.
Public protocol changesREVIEWUpdate only when focused/final or evidence semantics change.
Historical timings are evidence, not policy.The rebuilt suite's measured durations justify building an efficient selector, but no elapsed-time number belongs in the skill. Current performance is observed from current runs.

11 / Build order

Implement the protocol, then attack its assumptions

The future implementation remains scoped to the skill and AGENTS contract. Product topology and runner implementation stay outside its ownership.

1Capture baseline failuresRun E1-E13 without the skill and record broad reruns, stale assumptions, missing coverage claims, and evidence rejection.
2Create the stable skillAdd SKILL.md, discovery/escalation/evidence/review references, and agents/openai.yaml. Keep feature facts out.
3Publish the narrow contractUpdate AGENTS.md with focused/final commands and runner ownership; do not add topology or workflow prose.
4Run evolution pressureRerun E1-E13 with invented future names, renamed paths, deletions, refactors, and unrelated dirty changes; scan for snapshots and repeated commands.

12 / Evidence

Research and repository anchors

External sources support the model; repository facts determine the concrete shape.

Codex repository skills

Official skill documentation: repository skills live under .agents/skills, support implicit description-based triggering, and use progressive disclosure.

Codex instructions

Official AGENTS.md documentation: repository guidance forms a location-aware instruction chain and should hold durable project constraints.

Bazel action identity

Remote caching model: reusable results depend on declared inputs, command, and environment identity rather than elapsed time alone.

GitHub commit status

Commit status API: verification status is associated with a concrete commit/ref, supporting SHA-bound final evidence.

Test impact analysis

Microsoft TIA: impacted-test selection reduces regression cost. This design uses explicit ambiguity escalation and reserves repository-wide execution for FINAL.

Resource-based test size

Google test sizes and the Bazel Test Encyclopedia: resource ownership and exclusivity are more useful than vague unit/integration labels for execution policy.

Broad-test cost

Test Pyramid and Google flakiness study: broad-stack tests are slower and more failure-prone, so they should be signal-triggered.
