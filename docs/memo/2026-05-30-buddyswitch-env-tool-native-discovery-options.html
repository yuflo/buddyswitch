BuddySwitch Env Tool Native Discovery: Native-First Layer Governance Update

这版继续聚焦候选 A，并补上对“说明分散”的体系级审计。结论更严格： 候选 A 是正确基线，但单独的 MCP/action-native projection 还不够；最终方案应升级为 A+：native-first tool discovery，加上对 AGENTS、skills、context discovery、runtime tips 的说明治理。

更新后的主推荐： 采用 Action-Native MCP + Codex Native Tool Search Deferral。 也就是把每个 BuddySwitch env action 生成一个 typed native tool；当前 40 个 action 可直接暴露； 未来超过 Codex 阈值或启用 always-defer 时，交给 Codex 的 tool_search 按需发现和加载。

但这次审计确认，说明分散确实是当前 BuddySwitch tool/skill 体系的整体设计问题。 A 解决“Codex 调用前看不到 typed schema”的核心缺口；A+ 解决“旧 prose、tips、tests 继续把模型导向错误路径”的治理缺口。

1. BuddySwitch 当前事实

只读审计确认当前 BuddySwitch env surface 是 9 个 tool domain、40 个 action：

artifact: attach_file, create_revision, get, get_attachment, list, list_attachments, update_metadata
comment: add, list, resolve
context: get, list_sources, summarize
evidence: approve_downgrade, issue_browser
message: contacts, conversation, list, send
request: accept, block, cancel, complete, create, get, list
search: open_browser, request, status
task: confirm, current, propose
track: add_material, add_proof, add_update, archive, create, list, open, update_now

强点

  • ActionDefinition 已包含 name、description、input schema、output schema、权限、side effects、authority、durability、success effect、failure guarantee、use_when、do_not_use_when、risk hints。
  • ToolDefinition 已包含 tool description、scope、capability boundary、object model、use_when、do_not_use_when 和 actions。
  • registry.env_tools_description() 已能投影 operations、payload_fields、input_schemas、action_semantics。
  • 测试已经约束 shipped action schema 必须完整，字段要有 description，action 要有 use_when/do_not_use_when。

断点

  • CLI help 只有泛型 --payload JSON_OBJECT，不会进入 Codex native tool schema。
  • registry action 是 snake_case，例如 context.list_sources；CLI action 是 kebab-case，例如 context list-sources，会制造命名错觉。
  • skill 被测试要求不要复制 payload/action semantics，只能指向 runtime discovery。
  • runtime tips、AGENTS、skills、context sources 分别承担不同职责，任何一个写错都会把模型导向错误路径。
  • 当前没有把 BuddySwitch env actions 投影成 Codex MCP/native tools；因此 Codex 调用前看不到 typed input schema。
这说明 message 失败不是单个文案 bug，而是 native discovery 缺口在真实任务里显性化。 BuddySwitch 有权威 contract，但它还没有位于 Codex 做工具选择的那一层。

2. 说明分散审计

这次重新扫了 docs/bitter、runtime registry、context tools、47 个 skills、 5 个 buddy AGENTS、framework role contracts、runtime tips 和相关 tests。结论： “说明分散”不是 message 独有问题，而是当前分层设计的真实形态。

层 当前职责 审计结果 风险
Runtime catalog ToolDefinition / ActionDefinition 持有 schema、semantics、权限、side effects、use_when/do_not_use_when。 强。字段完整，校验严格，turn_runtime.py status 和 context.get.tool_catalog 都来自 registry projection。 不是 native tool surface，Codex 调用前仍看不到 action-level typed schema。
Context discovery context.get 暴露 full catalog；context.summarize 暴露 compact affordances；context.list_sources 只解释数据源。 职责基本正确。测试明确要求 summarize 不包含 input_schemas、payload_fields、action_semantics。 它是“再查一次才能知道怎么调工具”的 fallback，不等于 Codex native discovery。
Shared skills workflow note，引用 context.get.tool_catalog 和 turn_runtime.py status。 方向符合 docs/bitter：不复制 payload/action tables。但仍有大量 CLI 示例，且 CLI 被放在 Runtime Route 的第一位。 native tools 接入后，如果 skills 仍把 CLI 当主入口，会继续诱导模型绕开 Codex 原生能力。
Buddy AGENTS 角色边界、启动提示、常见 id-to-tool recipe。 5 个 AGENTS 都有同一处漂移：推荐 task get，但 registry 只有 task.current、task.propose、task.confirm。 这是系统级 prose drift，不是 message 局部 bug；现有测试还要求这个旧例子存在。
Runtime tips 事件触发提示，例如 [MESSAGE AVAILABLE]。 message.available tip 同时给 message_id 和 “Use message.list”，但 message.list 不接受 message_id。 tips 不是 schema source，却会被模型当作强指令，造成 payload 猜测。
Tests 防止旧工具、旧 payload、内部实现泄漏。 已有 skill drift guard，但缺少“所有 active prose command examples 必须对齐 registry”的通用校验。 局部测试可能把错误 prose 固化成合同，例如 task get。
审计结论： 当前分层本身是有逻辑的：runtime catalog 是权威，skills 写 workflow，context sources 写数据面，tips 写触发。 问题在于 Codex 缺少 native tool surface 时，这些辅助层被迫承担“工具发现/调用说明”的职责，最终产生漂移。

3. Codex 源码结论

对 /Users/chen/Dev/codex 的源码检查给出几个决定性事实。

源码证据 含义 对 BuddySwitch 的影响
mcp_tool_exposure.rs 定义 DIRECT_MCP_TOOL_EXPOSURE_THRESHOLD = 100，当 deferred MCP tools 数量达到阈值或启用 ToolSearchAlwaysDeferMcpTools 时，不直接暴露 MCP tools，而是放入 deferred surface。 Codex 原生已经考虑“大量 MCP tools 不适合全量塞进首轮”。 BuddySwitch 当前 40 个 action 低于阈值，可直接 action-native；未来变多时不需要自己写 pack engine。
tool_search_spec.rs 说明 tool_search 会“search deferred tool metadata with BM25”，并把匹配工具暴露给下一次模型调用。 大量工具的原生入口是 metadata search，不是手写说明表。 BuddySwitch 最重要的设计工作应是生成高质量 tool metadata，而不是继续扩写 skill prose。
tool_search_entry.rs 会把 search result 的 function/namespace tool 标记为 defer_loading=true 并移除 output schema。 Codex 把“可搜索但不预加载”作为一等机制处理。 BuddySwitch 可以在 native projection 中准备 defer-friendly 的 action tools。
handlers/tool_search.rs 用 BM25 建索引，默认 limit，按 query 返回 LoadableToolSpec，并合并 namespace results。 发现路径不是只靠 prompt 记忆，而是 runtime searchable index。 action 名称、description、schema 字段名和字段描述会直接影响召回。
handlers/mcp.rs 的 search_info() 使用 MCP tool info、namespace description 和 search text；测试验证 name、description、schema term 都能匹配。 MCP tool metadata 是原生搜索输入。 BuddySwitch env tools 如果走 MCP，正好进入 Codex 已有发现链路。
DynamicToolSpec 支持 namespace、name、description、inputSchema、deferLoading。 除了 MCP，Codex 也有 thread/dynamic tools 的延迟加载能力。 如果 BuddySwitch 未来通过 app-server/thread API 管 session，可以考虑 dynamic tools；当前更自然的是 MCP。
源码判断： 用户的直觉是对的。Codex 原生发现机制已经不只是“列 tools”，而是包含 direct exposure、deferred exposure、 BM25 search、namespace coalescing、dynamic tools defer loading、MCP enabled/disabled tools 等机制。

4. 外部实践结论

这次把外部资料分成“可作为架构依据的官方/源码/规范”和“只作经验参考的社区实验”。

来源 相关结论 对本决策的约束
OpenAI Tool Search guide Tool search 面向大量工具场景，建议工具少时直接用 function calling，工具多时用工具搜索按需发现。 BuddySwitch 不应把 100+ tools 全塞入首轮 context；但当前 40 actions 直接暴露仍合理。
OpenAI Agents SDK tools guide Agents SDK 把 hosted tools、function tools、agents-as-tools 分层处理，强调工具定义和 schema 是模型选择工具的重要输入。 工具颗粒度应保持可解释，不应把多个语义完全不同的 action 压进一个泛型 envelope。
OpenAI Apps SDK metadata optimization 工具和 app metadata 会影响模型何时选择工具、如何呈现和调用工具。 BuddySwitch 的 description/use_when/schema field description 不是文档装饰，而是检索和选择质量的核心。
MCP tools specification MCP tools/list 和 tools/call 的基本单元就是 named tool + description + inputSchema。 BuddySwitch 现有 ActionDefinition 很适合作为 MCP tool projection source。
Claude Agent SDK tool search Anthropic 也把大量工具场景抽象为搜索工具元数据，而不是全部预加载。 跨生态趋势支持“metadata index + deferred loading”，而不是 domain gateway。
Arcade 4,000 tool experiment 社区实验显示 tool search 可扩展到非常多工具，但复杂任务和描述质量仍会影响成功率。 只能证明方向可行，不能替代 BuddySwitch 自己的 smoke transcript 和 regression tests。
外部实践的共同点不是“工具越细越好”或“工具越少越好”，而是： 工具定义必须是可搜索、可区分、可调用的结构化 metadata；大规模时由原生 search/defer 机制控制首轮负载。

5. 旧三候选为什么不够决策

上一版的三个候选没有把 Codex 原生 large-tool discovery 纳入核心约束，所以容易误导决策。

旧候选 问题 新的处理
候选一：Action-Native MCP Surface 方向正确，但只回答“工具颗粒度”，没有回答“工具很多怎么办”。 保留并升级为 Action-Native MCP + Codex Tool Search Deferral。
候选二：Domain-Native Discriminated Tools 减少首轮工具数量，但把 action 语义藏进参数 schema，降低 native selection 和 search 质量。 降级为 fallback：只有当 host 不支持 native search/defer，才考虑。
候选三：Contextual Native Tool Packs 把 BuddySwitch 自己推向一套动态 pack/selection 系统，和 Codex 已有 tool_search 有重复。 不作为当前主方案；只保留“role/profile 过滤”和“event-specific hint”的轻量能力。
最需要避免的错误决策：因为担心未来 tools 很多，就过早压缩成 domain gateway。 对 Codex 来说，这会损失 action-level name/description/schema terms，反而削弱原生搜索与选择。

7. 推荐架构：A+

推荐的新架构是一个生成式 projection，不是新的业务 runtime。

7.1 单一权威源

  • ToolDefinition / ActionDefinition 继续是唯一权威 contract。
  • 不在 skills、AGENTS、tips、HTML 文档里复制 payload tables。
  • 所有 native tool name、description、input schema、risk/use_when 由 registry projection 从 per-tool definitions 生成，不能维护手写全局 action 清单。

7.2 MCP server surface

BuddySwitch Env Registry
  -> Native Tool Projection
  -> BuddySwitch Env MCP Server
  -> Codex MCP tool exposure
  -> direct tools when small
  -> deferred tools + tool_search when large
  • 每个 action 生成一个 named tool，例如 message_list、message_send、context_list_sources。
  • tool description 由 action description + use_when + do_not_use_when + authority/risk summary 组合。
  • input schema 直接来自 action schema，不再要求模型猜 --payload。
  • tool call 只转换到现有 env broker 调用，不复制业务逻辑。

7.3 大规模策略

  • 当前 40 action：低于 Codex 源码里的 100 MCP tool direct exposure threshold，直接 action-native 是合理基线。
  • 超过 100 action：依赖 Codex deferred MCP tools + tool_search，不做 BuddySwitch 自研 pack engine。
  • 角色过滤：用 active buddy/role 权限过滤 MCP tools/list 的可见集合，或用 Codex MCP enabled_tools/disabled_tools 做静态裁剪。
  • 事件提示：[MESSAGE AVAILABLE] 这类 runtime tips 只给最小触发信息，不再承载 schema 指南。

7.4 Skill 的正确位置

  • skill 仍然是 workflow note：什么时候检查 message、如何处理 PM 决策、何时沉淀 artifact。
  • skill 不应该复制工具参数表；这点当前测试方向是对的。
  • 但 skill 应明确说：首选 native env tools；只有 native surface 不可用时才回退到 context.get.tool_catalog 或 CLI。

7.5 说明治理规则

  • Native-first：Codex session 的主入口是 generated native tools；context.get / turn_runtime.py status 是诊断和 fallback；CLI 是人工 debug fallback。
  • AGENTS 瘦身：AGENTS 不应保留手写 action recipe。保留角色边界、native-first 原则、fallback discovery 位置，以及不直接编辑 runtime state 的硬规则。
  • Skills 限界：shared skills 写 workflow judgment 和验证方法，不写 action/payload/return tables；示例如果保留，必须由 registry 生成或被 registry 校验。
  • Context sources 限界：context.list_sources 只解释数据源；context.summarize 只做 compact orientation；full schema 只在 full catalog/native tools。
  • Tips 限界：runtime tips 只能陈述事件事实和语义目标，不携带 payload 暗示；例如 message.available 不应把 message_id 暗示成 message.list 参数。
  • 测试升级：新增 active prose command-example audit，扫描 AGENTS / active skills / role contracts 中的 python3 scripts/env/client.py <tool> <action>，并对照 registry CLI action 集合。

8. A+ 与并行解耦

重新按 docs/bitter/2026-05-28-parallel-change-boundary-principles.md 审视后，结论是： A+ 不天然冲突，反而可以增强解耦；但它有明确的落地红线。只要 A+ 变成“每个 action 都要改一个中央 MCP 清单”，它就违背并行边界原则。

并行边界原则 对 A+ 的约束 判断
普通工作应落在 product slice / tool package 内。 新增或修改 action 只能要求改 scripts/env/tools/<tool>/tool.py、该 tool 的 implementation、该 tool 的 focused tests。 A+ 必须满足
中央列表会变成冲突工厂。 Native projection 不能是 checked-in 手写 action manifest；它必须从 registry.supported_tools() / ToolDefinition.actions 生成。 A+ 安全条件
Public contracts 要小、稳定、显式。 MCP server 只暴露两个稳定动作：tools/list 由 registry projection 生成；tools/call 反向映射到 dispatch_env_tool_request。 不复制业务逻辑
Tool callers 只能消费 catalog / response semantics，不读私有 _impl.py。 Native projection 只读 ToolDefinition；不能 import env.tools.<tool>._impl、domain、repo。 已有测试方向支持
共享热点要显式保留或拆开。 registry.py、native projection、MCP server 是合法共享基础设施，但不得积累 per-action case logic。 需要新增边界测试
机械全局变更要序列化。 AGENTS/skills 从 CLI-first 改 native-first 是一次全局说明迁移，应单独短变更完成，不混入 tool 行为变更。 需要分批执行

8.1 A+ 的冲突形态

  • 手写 native manifest：每个 action 都要加一行到中央 MCP spec 文件。这会直接重现“one central registry where every feature adds an entry”。
  • MCP server action switch：server 内部按 action 写 if/elif 或 handler map。这会把每个 tool 变更拉回共享 runtime file。
  • 手写 per-role tool packs：按 PM/Dev/Market 手写可见 tool/action 列表。这会让角色可见性变成第二套权限真相源。
  • checked-in generated catalog：如果生成结果被人工编辑或频繁出现在 feature diff 里，它就是 lock-like 冲突文件。
  • central expected action tests：native projection 测试如果维护一个新的硬编码 action 表，会复制现有 registry 合同，增加更新面。
  • AGENTS 长手册修补：继续把 action recipes 写进 5 个 AGENTS，会让每个 tool 变更都产生 prose 更新。

8.2 A+ 的并行安全形态

scripts/env/tools/<tool>/tool.py
  owns ActionDefinition / ToolDefinition
        |
        v
env.tool_runtime.registry
  discovers tool packages and projects catalog
        |
        v
native projection
  generic conversion only: ActionDefinition -> MCP tool spec
        |
        v
MCP server
  tools/list from projection
  tools/call -> dispatch_env_tool_request
  • 新增 action 不改 MCP server、不改 AGENTS、不改 shared skill、不改全局 native action list。
  • 权限可见性从 ActionDefinition.required_permission + existing role_auth 推导，不新增 per-role action packs。
  • Projection tests 动态遍历 registry，断言每个 action 都有 native spec，native spec 与 action schema 等价；测试不维护第二张 expected action 表。
  • 如果必须生成文件，生成文件不能人工编辑，并且生成步骤作为单独机械变更合并。
  • AGENTS/skills 清理是一次说明边界迁移，目标是删除手写 recipes，而不是把 recipes 换一种写法。
并行结论： A+ 和解耦不冲突。正确的 A+ 是把 native discovery 作为稳定共享基础设施，把变更权仍留在 per-tool package。 错误的 A+ 会制造新的中央清单；那不是 A+，而是把旧痛点搬到 MCP 层。

9. 关键设计细节

问题 推荐处理 原因
tool 命名 优先 {domain}_{action}，例如 context_list_sources；不要用 CLI kebab-case。 减少 registry/CLI 双命名混乱，并让 search term 稳定。
namespace MCP server namespace 可用 buddyswitch_env，内部 action tool name 保持 domain/action 前缀。 Codex search 会 coalesce namespace；namespace description 应解释 BuddySwitch env tools 的边界。
description 短描述 + use_when + do_not_use_when + mutation/risk summary。 Codex 和外部实践都表明 metadata 是搜索和选择质量的核心输入。
schema 字段 保留现有 JSON Schema，字段 description 必须可读、可搜索、能区分相似 action。 Codex 测试确认 schema terms 能被 tool_search 匹配。
权限 MCP visibility 不能替代 env broker auth；调用时仍由 broker 做 role/permission 检查。 native discovery 只解决“看见和正确调用”，不应绕过产品权限。
tips tips 不写 schema；只提示事件事实和推荐动作语义，例如“有新 PM message，读取最新 messages”。 tips 是触发器，不是 contract source。

10. A 能解决什么，不能单独解决什么

问题 A 的效果 A+ 的追加要求
模型猜 payload / action 名 解决。typed native tools 让 schema 在工具选择和调用前可见。 保持 registry projection 是唯一 source，禁止手写 schema mirror。
大量 tools 的首轮负载 解决。Codex direct/deferred MCP exposure 和 tool_search 处理规模。 优化 metadata：name、description、use_when、schema field descriptions 都要可搜索。
AGENTS / skills prose drift 部分解决。native tools 降低 prose 的必要性，但不会自动删除旧 prose。 AGENTS 瘦身、skills native-first、示例校验、禁止测试固化 stale recipe。
Runtime tips 错误引导 部分解决。模型可查 native schema，但 tip 仍可能强烈误导。 tips event-only，不提供 payload 形状，不把事件 id 暗示成读取 action 参数。
Context discovery 职责 改变优先级。context catalog 不再是首选工具发现面。 保留 context 作为状态/数据/diagnostic surface；不要把它升级成另一个 native search 替代品。
结论： A 是必须的结构修复；A+ 才是完整产品质量修复。没有 A，说明治理只能继续靠 prompt bulk； 没有 A+，native tools 接上后旧说明仍可能把 Codex 拉回错误路径。

11. 为什么不是自己做 contextual packs

这点是本次调研后的最大变化。

  • Codex 已经有 direct/deferred exposure、BM25 metadata search、dynamic tools defer loading、namespace coalescing。
  • BuddySwitch 再做一套 pack selection，会引入第二个工具发现真相源，和 SHARP 的“少概念、短验证路径”相冲突。
  • 真正需要 BuddySwitch 控制的是角色权限、当前任务上下文、事件触发提示，而不是重建大规模工具搜索。
  • 如果以后发现 Codex tool_search 在 BuddySwitch 的真实任务里召回不足，应先优化 metadata 和测试查询，再考虑轻量 curated profiles。
contextual pack 可以作为未来的局部优化，但不应成为当前架构主干。 当前主干应是“权威 registry -> native typed tools -> Codex 原生发现”。

12. 如何验证这个推荐

13. 最终结论

所有 BuddySwitch env tools 不是“不符合 Codex 原生发现机制”这么简单；更精确地说： BuddySwitch 已有 env tool contract，但它还没有被投影到 Codex 原生工具发现层。 因此 Codex 当前只能通过 skill/context/CLI/tips 间接理解，容易猜错。

大量工具问题不应该推动 BuddySwitch 走 domain gateway 或自研 contextual pack。 Codex 源码已经提供原生路径：100 以下 direct MCP exposure，更多时 deferred MCP + tool_search； dynamic tools 也支持 deferLoading。BuddySwitch 最该做的是把 action contract 变成高质量 native metadata。

但候选 A 需要升级成 A+：native tools 是主发现面；AGENTS/skills/tips 退回各自边界； context catalog 保留为状态和诊断 fallback；所有 active prose examples 必须由 registry 校验。 这才符合 docs/bitter：不要用大 prompt、phrase triggers、长 AGENTS 手册补偿不清晰的 tool contract。

A+ 与并行解耦不冲突，但必须以 per-tool definition + registry discovery + generic projection 方式落地。 不能新增手写 native action manifest、per-role tool pack、MCP action switch、checked-in 人工编辑 catalog。 并行开发的意义不是让大家更努力合并冲突，而是让普通 tool 变更根本不需要碰同一个共享文件。

决策建议： 选候选 A+：Action-Native MCP + Codex Tool Search Deferral + Native-First Layer Governance。 候选 B 作为未来 app-server/thread-managed session 的替代入口；候选 C 只作为非 Codex host 或原生 discovery 不可用时的 fallback。
