剩余 BuddySwitch 问题

1. instance stop 没有完整释放 browser runtime

high

instance stop 进入 instance_set_inactive_locked 后只调用 buddyswitch_browser_instance_stop。它只看 browser/chrome.pid， 不停 runtime/browser/cockpit-upstream.pid/pgid，不清 page_idle.json， 也不清 browser_port。

  • 影响：actor 被停掉后，upstream MCP 和 browser runtime state 可残留。
  • 优化方向：新增或复用“强制实例级 cleanup”，只清 actor marker 资源，不碰宿主 9222。
  • 证据：buddyswitch-codex:363-379，browser_cockpit.sh:871-1002。

2. list_pages 会启动资源，但没有空闲释放闭环

high

proxy 对任何 tools/call 都先 ensure_browser_url。 list_pages 会 forwarded 到 upstream 并追加 state，但在无 tracked page 时没有调度 browser.cockpit.release。

  • 影响：只查看页面也可能启动 Chrome/upstream，然后无人负责释放。
  • 优化方向：list_pages 成功后如果 page_idle.targets 为空，排一次 release；release handler 仍保护真实页面。
  • 证据：chrome_devtools_cockpit_proxy.py:451-452、:612-615、:975-982。

3. Chrome ensure 失败时可能留下无 marker 进程

high

browser_cockpit.sh 启动 Chrome 后写 chrome.pid。如果 20 次探测仍未 ready， 当前路径只删除 marker，没有杀刚启动的 PID/PGID。

  • 影响：进程存在但 BuddySwitch marker 丢失，后续 stop/release 更难定位。
  • 优化方向：失败分支调用现有 terminate helper 杀 chrome_pid，再删 marker。
  • 证据：browser_cockpit.sh:667-704。

4. release real-page no-op 合理，但缺少观测

medium

release handler 看到真实用户页面会直接 handled/no-op。这保护用户页面是对的，但当前没有明确记录跳过原因。

  • 影响：排查时看不到“因为 real user page 所以跳过”。
  • 优化方向：只增加可观测 reason；自动 retry 单独决策，避免把清理修复扩成调度策略。
  • 证据：browser_release_handler.py:142-146。

建议的优化包

P0

Stop cleanup 闭环

让 instance stop 停 upstream PGID、停 actor Chrome marker、清 page idle、清 browser_port。

P0

Ensure failure cleanup

Chrome 未 ready 时杀刚启动 PID/PGID，避免无 marker 进程。

P1

list_pages idle release

无 tracked page 时调度 release，让 read-only browser call 也有释放闭环。

P2 / separate

Release skip observability

记录 real-page no-op reason；retry 策略不并入 P0/P1 生命周期修复。

范围边界

  • 只关注 BuddySwitch: actor-owned Chrome、cockpit proxy、upstream MCP、daemon release trigger、instance runtime state。
  • 不归 BuddySwitch actor 管: 宿主 Codex 的 chrome-devtools-market --browser-url=9222，以及用户/其它 Codex 会话的浏览器。
  • search.open_browser 仅是调用方: search 层只构造 URL 并调用 browser-session；本轮不在 search 层新增 ensure、release、cleanup 逻辑。
  • 本轮没有新建 actor: 现场已有其它 actor 测试进程，报告使用静态审计和定向 pytest 证据。

对焦问题

  1. instance stop 是否应强制清 actor browser? 建议是 yes，只杀 marker/pgid 归属资源，不按端口杀 foreign。
  2. list_pages-only 是否应该短延迟 release? 建议是 yes；真实页面保护留给 release handler。
  3. real-page no-op 是否自动 retry? 不进本轮 P0/P1；建议先只记录 reason，retry 需要单独防循环策略。
  4. diagnose --json 是否进入同一包? 建议暂不进 P0/P1 修复包，避免把生命周期修复扩成工具平台。
