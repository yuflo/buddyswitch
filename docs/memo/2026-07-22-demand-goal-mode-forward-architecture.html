Demand intake · side-owned judgment

Demand Triage：先判断，再决定是否形成需求

这是对当前 capture-first 流程的根本替换。Inbound 不再先创建临时 Demand；side 不向 parent 移交判断，也不存在 needs_parent_judgment。

Exact side output

TriageProposal

语义判断全部在 isolated side 完成；Codex 用 per-turn outputSchema 约束最终消息。Side 不写 Demand，也不处理 intake key、provenance、receipt 或 CAS。

create

创建独立 Demand

存在尚未满足的新义务，与现有 live Demand 不是同一底层需求。

merge_intake

补充现有 Demand

Side 只指明目标与语义补充；source provenance 合并和原子写入由 host/domain 完成。

revise

修正需求含义

不是简单加法，而是改变目标、边界或约束；保留 provenance。

cancel

撤回现有 Demand

Inbound 明确表明需求不再需要满足；side 给出语义理由，版本校验与 terminal 写入由 host/domain 完成。

context

Side 必须 context-complete

完整 inbound fact、必要 conversation window、live index、候选 Demand 详情、active Goal/Task 摘要、允许的 source-local capability。

concurrency

冲突重算，不升级 Parent

Host apply 遇到 revision conflict 时，使用最新 Demand context 重新运行 triage side；这是并发 re-evaluation，不是让 Actor 手工重试 CAS。

删除 action、terminal type、target_demand_id、skill 规则、UI/CLI/测试和架构文档中的现行教学。

actor-created demand

Actor 自建 Demand 继续保留直接入口

Actor 在 parent turn 或 Goal working 中发现一个新的、对外有意义的未满足义务时，调用收窄后的 demand_sys.create，只表达 description 与 detail。Host 从调用上下文派生 provenance/idempotency，不要求 Agent 制造 key 或底层 refs。新 Demand 进入同一个 live pool，但不会自动创建 Task、替换当前 Goal 或打断执行。

判定线：若只是满足当前 Demand 的下一执行步骤，不创建新 Demand；让当前 Demand 保持 live，并在下一次 reconciliation 中形成新的 Task objective。只有底层需要独立存在、独立完成时才创建新 Demand。

one state owner

Inbound 与 Actor self-demand 共用一个 Demand 真相

两条入口不同，但写入后没有两类 Demand：inbound 通过 capture_intake → TriageProposal → internal apply；Actor self-demand 通过高层 create。二者都进入同一 actor-owned aggregate、同一 revision/lifecycle、同一 selection pool。

Goal active 时新增或修改 Demand 只合并 pool_changed attention，不 steer、不 interrupt；Goal complete 后由 orchestration 统一重新比较全部 live Demands。

Three vertical implementation stages

三阶段实施：每一步都形成闭环，每一步都完成替换

Contract 冻结不是单独的 P0，历史清理也不是最后才做的 P5。每一阶段都以 contract / RED proof 开始，以产品验证、替换清理和 residue assertion 结束；只有通过出口 Gate 才能进入下一阶段。

阶段含义：可以是连续 commit/PR 检查点，但不能成为 runtime mode。任一已接受版本，对同一语义只能有一个 owner、一个 write path 和一个 Skill 规则来源。
切换纪律：不增加 compatibility alias、feature flag、fallback read、dual write、旧 schema 解析器或旧 Skill 转发器；被替换路径必须在本阶段删除。
S1
Demand Intake REBUILD

把 inbound 串行检查改成 side 并发形成 canonical Demand pool。

  • 入口冻结：TriageProposal decisions、source-local handled allowlist、host invocation identity 与六工具 contract。
  • 建立：pending intake、outputSchema 透传/final-output extraction、isolated demand-triage、私有 proposal apply、receipt/CAS/retry。
  • Skill 切分：demand-triage 唯一拥有 intake 判断；demand-orchestration 唯一拥有 selection/reconciliation；旧 task-management 暂时只拥有尚未替换的 Task frame 执行。
出口证明 + 删除

浏览器多条 inbound 可产生 create / merge_intake / no-demand，side 并发且不 steer parent；idle 时仍能经唯一的 orchestration owner 选择至多一个现行 Task。删除 [DEMAND CHECK]、check cursor、get_many/check/complete_check/absorb_into、raw revision payload 及其权限/教学/测试。

S2
Single Demand → Goal REBUILD

用 Codex Goal 一次性替换 Task 自有执行状态机。

  • 入口冻结：Task/Goal 启动握手、result-before-complete 顺序、complete/blocked/clear 最小状态映射与重启恢复。
  • 建立：独立 task identity、DemandRef、selection reason、objective、Goal/thread binding、durable result；注册 Goal updated handler。
  • 主闭环：idle pool selection → minimal Task → Goal working → terminal receipt → 同一 main thread 新 orchestration turn → Demand reconciliation。
出口证明 + 删除

一个 Demand 跨 turn 由 Goal 完整执行，拒绝第二个 unfinished Goal，握手任一点重启不产生孤儿。同期删除 side/parent/outcome frames、Progress Check、need_parent/close 旧语义、processor/lease 状态与 task-management。

S3
Multi-Demand Orchestration + Acceptance

在同一组 owner 上扩展多需求调度、恢复和用户交付。

  • 入口冻结：Selection Contract、当前 Demand 连续性规则、pool attention 合并、全部 Goal 非 complete 状态映射与消息交付 evidence。
  • 建立：Goal active 时并发 triage、pool_changed coalescing、terminal 后全量 live pool 比较、keep-live Demand 的后续 Task、daemon/app-server recovery。
  • 产品实测：Market 两独立 + 两补充需求；Dev 自主创建 Demand；最终结果回到 Web 消息会话。
出口证明 + 全局审计

只启动一个下一 Task/Goal；重复通知与重启不重复执行或丢失 Demand；用户可读正文而非只见 artifact metadata。扫描 schema、actions、role_auth、manifest、skills、roles、runtime prompts、DTO/UI/CLI、tests 与 docs/arch，旧模型仅可出现在 Git、历史 memo 或负向残留断言中。

REBUILD acceptance gate

分阶段不等于双轨：每个阶段只有一份当前真相
