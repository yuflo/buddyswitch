BuddySwitch IM architecture memo

6-8：actor target message handling 重建边界

这个 HTML 帮助锁定 1-5 完成后的下一段改造：把已写入 Central IM 的 actor-target message 交给目标 actor runtime 处理，同时不把 target 处理细节反向塞回 sender 写消息流程。

目标

只处理 actor target

本轮 6-8 只处理 target 是 actor 的 message handling；to external 的通道处理先 pass。

主边界

1-5 写入，6-8 处理

1-5 产出 message refs；6-8 以 refs 和 target identity 进入目标 actor 本地处理链路。

原则

不做加法，不留双轨

删除 target_role_id / wake_actor 对 1-5 的耦合，不新增通用 delivery engine。

1. 本次任务目标

目标：把当前混在 send_im_message 内部的 actor wake / mailbox / local handling 拆回 6-8，让 sender 视角的 Central IM 写入完成后，再由 actor-target handling 链路接手。

只处理 target actor 不处理 target external 不改变 IM 持久化模型 不新增 generic delivery engine

2. 现状：6-8 被塞进了 1-5

1-5
Central IM 写入其实已经可以只按 identity 完成
send_im_message 写 direct conversation、message、target state、sender/target visible events。这里需要的是 sender identity、target identity、content、reply_to。
6
但同一个函数继续构造 actor wake payload
当前 send_im_message 接收 target_role_id 和 wake_actor，写完 message 后直接进入 actor wake 分支。
7
sender 侧必须知道 target 处理细节
由于 wake payload 需要 target_role_id，sender reach 阶段被迫解析目标 actor 的处理路由。
8
处理结果回流到 message write response
wake_status 被放进 send_im_message 返回，使 actor handling 状态看起来像 message 写入成功条件的一部分。

3. 目标形态：6-8 的系统流

1-5 输出

message_id、conversation_id、event_id、target_identity。这些 refs 由 Central IM 写入路径自动生成、复用或解析。

6. actor handling adapter

仅当 target_identity.type == actor 时进入。输入是 target identity id 和 message refs，不接收 sender 提供的 role。

7. target runtime route

从 identity module 读取 actor profile 的 role_id；从 daemon reachability 读取 online 状态和 mailbox endpoint。

8. local actor event

向目标 actor mailbox 投递 im.message.created local trigger；后续由目标 actor runtime 的本地消费者处理。

6. Task Sys 的正确位置

Task Sys 不是 6-8 rebuild 的主语。它只是当前目标 actor runtime 消费 inbound event 的一种现行实现。6-8 的架构目标是把 message refs 可靠交给 target actor 本地 runtime，不能把 Task Sys 作为跨模块边界的中心概念。

可以提及
不能变成主目标
现有 ImMessageCreatedHandler 尾端会调用当前 runtime 消费入口。
不能把 6-8 写成“创建 Task Sys task”的改造。那是目标 actor runtime 内部消费策略，不是 message handling adapter 的职责。
测试可以覆盖现有 consumer 没被破坏。
不能让 Task Sys 的字段、状态或生命周期反向决定 1-5 / 6-8 的接口形态。

8. 可靠性与注意事项

必须保持

  • 1-5 写入成功不因为 actor mailbox 暂时不可达而被回滚。
  • 6-8 处理 actor target 时，输入只使用 target identity 和 message refs。
  • message refs 中 conversation_id 是输出 ref，不是 sender 输入。
  • external target 的 outbound/channel 处理不在本轮设计内。

需要警惕

  • 不要引入 generic delivery engine、event bus、outbox 等新层。
  • 不要让 send_im_message 同时保留新旧签名。
  • 不要把 Task Sys 消费策略写成 6-8 的主边界。
  • 不要让 daemon reachability 继续复制 identity profile。

9. 验收判断

  • send_im_message 签名不再包含 target_role_id / wake_actor。
  • send_im_message 返回不再用 wake_status 表示 actor handling 状态。
  • actor target 的 6-8 入口只接收 target_identity_id 和 message_id/conversation_id/event_id。
  • 6-8 从 identity module 获取 actor profile / role_id。
  • 6-8 从 daemon reachability 获取 online 状态和 mailbox endpoint。
  • mailbox.local_trigger 仍可携带 identity_id + role_id，但 role 必须是 target-side 派生，不来自 sender。
  • 现有 actor-target message 可以进入目标 actor runtime 本地 inbound event。
  • target external 的处理不作为本轮验收项。

11. 最短执行拆分

A
先改 message service 边界
移除 send_im_message 对 target_role_id、wake_actor、wake_status 的依赖，保留纯 Central IM 写入行为。
B
再改 actor handling adapter
重塑 wake_im_actor 或等价入口：只接收 actor target identity + message refs，内部读取 identity profile 和 reachability。
C
最后调整调用方与测试
Actor tool、external-to-actor 入口、Web IM 等调用方在 message write 后进入同一 6-8 入口；测试拆成 message write 与 actor handling 两组。
Artifact job: 让后续实现只围绕 actor target 的 6-8 message handling 边界推进，避免把 target external、Task Sys 策略、generic delivery 层混入本次任务。
