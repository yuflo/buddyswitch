Daemon 不是某个业务的后台进程，而是 actor runtime 的守护与协作层。

这份分享面向 message 团队和后续接入 daemon 的业务团队。它说明 daemon 当前已经交付的能力、我们认为正确的架构边界，以及近期必须完成的解耦方向。

daemon guards each actor runtime and provides online actor coordination: presence, reachability, cross-actor signal delivery, signal handling, and local action triggering.

1. Daemon 的产品定位

daemon 团队负责守护本地 actor runtime，并提供跨 actor 在线协作能力；不是把各业务系统搬进 daemon。

Correct framing

central daemon + instance daemon

central daemon 是 actor network control plane，维护在线 registry、contacts、reachability、delivery routing。 instance daemon 是每个 buddy instance 的 runtime sidecar，接收本地/远程信号并通过 ActionGateway 唤醒本地 actor。

Wrong framing

业务后台或流程引擎

daemon 不保存 message 正文，不判断 task 生命周期，不处理 request/artifact/comment 的业务状态，也不做通用 workflow engine。 业务规则属于业务模块；daemon 提供 runtime 守护、在线协作和受控 action 触发底座。

2. 三层能力

从业务团队视角，daemon 暴露的是 presence、communication、execution 三条主能力。

Presence Plane

谁在线，谁可达

daemon 启动后注册自己的 actor_address、endpoint、heartbeat、status。central daemon 提供 contacts.list 和 actor.check_reachability。

Communication Plane

跨 actor 在线信号投递

业务传入明确 target_actor_address。central daemon 只向在线 target daemon 投递信号；离线不持久化，不替业务存数据。

Execution Plane

目标 daemon 本地触发

target daemon 接收 signal 后分发给 handler。handler 如需影响 buddy，只能通过 ActionGateway，例如 submit_turn。

5. 业务团队如何接入 daemon

业务团队接入 daemon，不是把业务逻辑交给 daemon，而是使用 daemon 的在线协作能力。

1

持久数据归业务

message、task、request 等业务对象由各自模块写入自己的 repo。

2

发现在线 actor

需要时调用 contacts / reachability。已有明确地址时不强制查询。

3

构造业务 signal

业务决定 type 和 payload；daemon 只要求明确 source / target actor。

4

central daemon route

只向当前 online target daemon 投递，不替业务做离线保存。

5

target mailbox ingress

目标 daemon 校验 target actor，并把 signal 交给本地 dispatcher。

6

handler owns semantics

业务 handler 校验 payload，决定要不要触发本地 actor。

7

ActionGateway only

handler 通过 submit_turn 等受控入口影响本地 buddy。

6. Message 团队接入方式

message 是 daemon communication plane 的第一个跨 actor 业务消费者，但 message 数据仍属于 message。

升级后 message 主链路

message.send(target_actor_address, content)
  -> check reachability through central daemon
  -> reject if target is not online
  -> create durable message object
  -> deliver signal through daemon
  -> target daemon handler submit read prompt
  -> target buddy calls message.list

业务 signal 的建议形态

{
  "signal_id": "sig-...",
  "source": "mailbox",
  "type": "message.available",
  "source_actor_address": {...},
  "target_actor_address": {...},
  "payload": {
    "message_id": "msg-..."
  },
  "created_at": "..."
}
message 正文不进入 daemon event，不进入 mailbox，不写接收方 daemon 目录。daemon 只投递“有一条 message 可读”的在线信号；message durable store 才是数据事实。

7. 近期迭代规划

这不是长期平台蓝图，而是为了让 message 和后续业务接入时边界不被污染的近期工作。

P0 · event 解耦

引入 generic signal envelope

mailbox 不再理解 message_id 或 message.available 字段，只校验通用 envelope 和 target actor。

P1 · ingress 分层

local / remote 入口保持清晰

Task TUI 继续走本地 runtime notification；remote mailbox event 解耦为通用 DaemonSignalEnvelope。两条线共享 ActionGateway 和 handler state。

P2 · handler contract

收敛 handler 接口

业务 handler 实现 handle_signal，返回 ignored / handled / failed；daemon 记录状态和错误。

P3 · message 接入

message 作为消费者

message.send 使用 daemon reachability + signal delivery；MessageAvailableHandler 负责 payload 校验和 read prompt。

8. 给业务团队的契约

接入 daemon 时，业务团队只需要记住这几条硬边界。

You own

业务数据和业务规则

message owns durable message object；task owns task snapshot and TUI semantics；future business modules own their payload validation and object lifecycle.

Daemon owns

在线协作和本地触发

daemon owns presence, reachability, online signal delivery, mailbox ingress, signal dispatch, handler state, and ActionGateway.

Do not ask daemon to

保存业务事实

不要把正文、对象状态、业务权限、离线队列交给 daemon。需要持久化就写入业务 store。

Do not couple

不要把业务 shape 放进 mailbox

mailbox 只能认识 daemon signal envelope。具体业务 payload 应由 typed handler 解释。
