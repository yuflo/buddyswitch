Precise proposal for BuddySwitch actors

任务系统是能力，innerTUI 是 actor 看见它的地方。

我们要做的不是一组离散 task tools，也不是把 prompt 包装成 TUI。我们要做一个 actor 使用的任务管理系统，并把它的全部可见内容通过 innerTUI 呈现。

One sentence: Task System owns task truth and operations; innerTUI owns every actor-visible task surface; tools are only API adapters.

Highlight：这次要确认的点。

基于当前 v2 页面、task 代码、taskbox 存储和 docs/bitter 原则，这里只保留会影响架构和实施的要点。

01
actor 是使用者，不是被系统管理的对象。 系统提供工作台、状态、操作、证据和提醒；语义判断仍由 actor 做。
02
innerTUI 是全部 actor-visible task surface。 当前任务、shelf、pending switch、动作、checkout、证据、warnings 都是 innerTUI scope，不是 prompt wrapper。
03
所有 task tools 必须从 Task System 长出来。 工具只暴露系统操作；不能各自定义 finish、block、switch 的产品语义。
04
存储继续是 taskbox，但 taskbox 不是产品边界。 taskbox 是 Task Core 的 storage backend；actor、tools、innerTUI 都不直接把它当产品 API。
!
不做双轨。 实施时替换旧的离散 task.propose/confirm 语义，不长期保留新旧两套 actor-facing 操作。
!
不靠 prompt 补契约。 工具契约、response feedback、TaskViewModel、innerTUI surface 必须自己说清楚状态影响。
!
不在 shared layer 堆特殊分支。 task 变化落在 task product slice；message/request/artifact 只作为 relation input 或 refs 进入。
!
测试同时验证行为和 live surface。 行为测试证明状态正确；surface scan 证明 actor 现在不会再看到旧语义。

整体系统设计：一条产品链路。

架构上只保留一个方向：actor 通过 innerTUI 看见任务产品，通过 task tools 使用 Task Operations，最终由 Task Core 写入 taskbox。

Chain

不要让任何一层绕过 Task System。

actor judges meaning and chooses the task action
innerTUI renders every task-management surface visible to actor
task tools expose system operations as the API entry points
Task Management System owns model, rules, operations, events, and TaskViewModel
taskbox stores task docs, current pointer data, events, evidence refs, and timestamps
Boundary

当前代码证据和新边界。

  • scripts/env/repos/tasks.py 已经是 instance-local taskbox backend。
  • scripts/env/domain/task_management.py 应成为唯一任务领域系统，而不是 propose helper。
  • scripts/env/tools/task 应只适配 Task Operations，不承载独立产品语义。
  • scripts/env/domain/task_tui.py 是 innerTUI task surface 的渲染入口。
  • buddyswitch/skills/shared/task-management 只教 actor 判断和使用，不复制状态机。
  • 低耦合边界：task product slice 拥有 task 状态；其他 runtime objects 只通过 refs/origin 进入，不互相改 sibling internals。
Model

Task Core 的最小事实模型。

captured 被 actor 收进 shelf 的工作；不会自动成为 current anchor。
active 当前 anchor 指向的工作；任意时刻最多一个。
blocked actor 明确留下阻塞原因和证据；后续由 review cue 唤回。
done checkout 或 finish 操作带证据关闭；不再作为 active/shelf 展示。
  • Task: id, title, brief/body, status, priority, origin, refs, progress_summary, timestamps。
  • TaskEvent: captured, selected, switch_requested, switch_confirmed, progress_appended, checkout_continued, blocked, finished。
  • TaskViewModel: current anchor, shelf, pending switch, recent evidence, available operations, checkout cue, warnings。
Operations

Task Operations 是唯一语义来源。

current读取 TaskViewModel；不改变 taskbox。
capture创建 captured task；不切 current。
select在没有 active anchor 时从 shelf 选为 current。
switch_request有 active anchor 时只创建 pending switch。
switch_confirmactor 明确接受后才替换 current anchor。
progress追加进展摘要、evidence 和 refs。
checkoutcontinue、finish、block 的统一工作块收口。
review展示 blocked/stale/captured items 的回看 cue。

innerTUI 的定义要放大。

innerTUI 不是 prompt 收纳，也不是 task system 的一个小模块。它是所有 built-for-actor 产品被 actor 看到和使用的统一界面/内容层。

Scope

任务管理系统里，actor 看见的一切都属于 innerTUI。

  • 当前任务、状态、进展摘要。
  • shelf/backlog、pending switch、blocked review cue。
  • 可用动作、限制、checkout 提醒、证据要求。
  • 系统希望 actor 做出的下一步任务判断。
Not this

不要把 innerTUI 理解成 prompt wrapper。

  • 不是把提示文案换个框展示。
  • 不是 task.current 的 prettified output。
  • 不是某个功能的局部 UI。
  • 它是 actor product 的统一可见层。

tools 必须从 Task System 长出来。

task 相关 tools 是系统操作入口，不独立定义语义、不绕过状态机、不各自生成 actor-facing 内容。

Task System owns

state model, legal transitions, evidence rules, view model, operation semantics。

Tools expose

task.current, task.capture, task.select, task.switch_request, task.switch_confirm, task.progress, task.checkout, task.review。

innerTUI renders

TaskViewModel: anchor, shelf, pending switch, evidence, available actions, checkout cue。

Rule

No standalone tool semantics

新增工具不能自己解释什么是 finish、block、switch；旧的 propose/confirm 也不作为长期 actor-facing 双轨保留。

Rule

No bypassing state machine

所有 mutation 都经过 Task System 的合法流转和 evidence rule。

Rule

No scattered actor-facing output

actor 看到的任务内容统一由 TaskViewModel 进入 innerTUI。

Rule

Actor owns judgment

系统提供结构和约束；actor 判断输入关系、做工作、提交证据。

actor 使用流程：一条线。

展示给团队时，这条线最重要。所有工具、状态、innerTUI 都服务这条 actor 工作线。

1 See anchor

innerTUI 展示当前任务、进展、pending switch。

2 Judge input

actor 判断继续、capture、switch、progress 或 none。

3 Use operation

actor 通过 task tools 调用 Task Operations。

4 Record truth

Task Core 写入 task state、event、evidence。

5 Resume / checkout

innerTUI 在下一轮或 checkout 显示最新状态。

实施方案：一次替换成系统。

当前瓶颈不是缺一个工具名，而是 task 语义分散在 tool、skill、TUI cue 和 propose/confirm 里。实施时直接把它们收回 Task Management System。

Files

文件边界按 task product slice 收敛。

scripts/env/repos/tasks.py taskbox backend：负责 task docs、history/events、id、持久化校验。
scripts/env/domain/task_management.py Task Management System：负责状态机、操作语义、evidence rules、TaskViewModel。
scripts/env/tools/task/tool.py tool catalog：暴露 current/capture/select/switch_request/switch_confirm/progress/checkout/review。
scripts/env/tools/task/_impl.py tool adapter：只调用 Task Operations 并返回结构化 tool feedback。
scripts/env/domain/task_tui.py innerTUI task surface：只渲染 TaskViewModel，不再写离散操作提示。
buddyswitch/skills/shared/task-management/SKILL.md actor 使用说明：只教判断和使用系统，不复制 payload schema。
No residue

替换规则。

  • 删除 live surface 里的 task.propose(start/switch/finish/block) 指南。
  • 删除把 task.confirm 当独立产品语义的表达；它并入 switch_confirm。
  • 不在 tools 层加兼容 alias，不保留新旧两套 actor-facing action。
  • 不改 buddyswitch/objects/**；runtime state 仍通过 env tools 和 taskbox backend 写入。
  • 不让 message/request/artifact 拥有 task 状态；它们只提供 refs、origin、relation input。
Step 1

Rebuild core model

  • 在 taskbox task doc 中明确 captured/active/blocked/done。
  • 把 current anchor 从 history 推导整理成系统级 current pointer 语义。
  • 新增 TaskEvent 类型和 evidence refs 写入规则。
Step 2

Replace tool surface

  • 把 task.propose 拆成明确 Task Operations。
  • tool response 必须说明 state_changed、durability、created/updated ids、allowed next actions。
  • 拒绝请求必须证明 taskbox 和共享对象均未改变。
Step 3

Replace actor surface

  • innerTUI 渲染 TaskViewModel：anchor、shelf、pending switch、actions、evidence、checkout。
  • checkout 只提供 continue/finish/block 的系统操作入口。
  • skill 和 compact affordance 只引用新操作语义。

测试要点：行为和表面都要过。

这次不是只测 action 注册。测试必须证明 taskbox 状态、tool feedback、innerTUI 内容和 live surface 没有旧语义残留。

Matrix

必须覆盖的行为。

captureactive task 存在时，capture 只进入 shelf，不替换 current anchor。
select没有 active anchor 时才能从 captured 选中；有 active 时必须走 switch_request。
switchrequest 只创建 pending switch；confirm accept 才切 current；reject 保持原 anchor。
progress追加 event、progress summary、refs/evidence；不发布 track/artifact/message 状态。
checkoutfinish 必须有 evidence；block 必须有 reason；continue 不关闭任务。
rejection非法 payload、错误 task_id、重复 pending switch 都必须 state_changed=false。
Surface

live surface 残留检查。

  • scripts/env/domain/task_tui.py 不再出现 Task Handling Cue、task.propose(...)、task.confirm 旧提示。
  • buddyswitch/skills/shared/task-management/SKILL.md 不再把 propose/confirm 当 actor-facing 操作。
  • scripts/env/tools/task/tool.py 的 catalog 只描述新 Task Operations。
  • tests/test_task_management_skill_architecture.py 保证 skill 不复制 runtime schema，不绕过 tool catalog。
  • 只扫描 live surfaces，不把旧 memo 或历史记录当 cleanup target。

Decision

团队要对齐的不是“加几个 task tools”，而是“一次替换成一个 Task Management System”。

最小清晰形态：Task Core 存真相，Task Operations 定义动作，taskbox 作为 storage backend，tools 只是系统 API surface，innerTUI 展示 actor 看见的一切。实施时不保留离散 propose/confirm 双轨，测试同时证明行为和 live surface。
