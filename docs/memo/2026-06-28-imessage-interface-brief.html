BuddySwitch memo · 2026-06-28

iPhone ↔ Mac iMessage 接入 BuddySwitch：可行性与方案简报

目标：快速理解整体思路、方案取舍、关键集成点、风险和应对策略。

一句话结论

这件事可行，但不是 iPhone 直接连接 BuddySwitch；可行路径是： iPhone 的 iMessage 同步到一台已登录 Messages.app 的 Mac，Mac 上运行一个本地 bridge， 通过 imsg 读取/监听/发送，再映射进 BuddySwitch 现有 Central IM。

推荐路径 Mac 本地 imsg bridge MVP。
不建议先做 群聊、附件、tapback、已读、typing indicators。
核心原则 iMessage 只是外部 IM 适配器，不进入 BuddySwitch 核心消息模型。

技术心智模型

iPhone iMessage -> Mac Messages.app -> imsg rpc / watch -> buddyswitch-imessage-bridge -> BuddySwitch /api/im/messages -> actor wake + message tool -> BuddySwitch /api/im/events -> imsg send -> iPhone iMessage

OpenClaw 的实践也指向同一类路径：通过 imsg rpc 作为本地 JSON-RPC 子进程， 读取和监听 Messages，并通过 Messages.app 自动化发送。关键约束是 Mac 必须能运行 Messages.app， 且启动 imsg 的进程具备对应 macOS 权限。

方案取舍

方案 做法 优点 代价 / 风险 判断
A. Mac 本地 imsg bridge bridge 与 Messages.app 跑在同一台 Mac，直接调用 imsg rpc 和 BuddySwitch IM API。 路径最短；不引入外部服务；最容易做可验证 MVP。 依赖 macOS 权限、Messages.app 登录状态、imsg 稳定性。 推荐
B. 远程 Mac / SSH bridge BuddySwitch 可在别的机器，bridge 通过 SSH 到 Mac 执行 imsg。 部署更灵活；保留 Mac 作为 iMessage 网关。 多一层 SSH 凭据、网络、日志和故障面。 第二阶段再做
C. 第三方 iMessage relay 使用外部中继或商业接口，BuddySwitch 对接 relay API。 可能避开本地 Mac 权限问题。 隐私、成本、供应商锁定、可靠性和合规风险更大。 不作为首选

推荐设计：本地 bridge MVP

职责边界

  • Bridge 只负责 iMessage 与 BuddySwitch Central IM 之间的协议转换、去重、状态保存和健康检查。
  • BuddySwitch 继续拥有消息模型、actor wake、权限和回复语义。
  • Actor 继续使用现有 message.get、message.send(reply_to=...)、message.mark。

MVP 功能

  • 只支持一对一文本消息。
  • 配置 allowlist：允许的 phone/email/chat_id 与目标 target_identity_id。
  • 每个 iMessage chat 绑定一个 BuddySwitch external IM connection。
  • 入站 iMessage 调用 POST /api/im/messages。
  • 出站 actor 回复通过 GET /api/im/events 拉取，再用 imsg send 发回原 chat。
  • 本地保存 chat_id、connection_key、目标 actor、last row/guid、发送状态。

不进入第一版

  • 群聊 routing 和 mention 规则。
  • 图片、语音、文件附件。
  • tapback、已读、撤回、编辑、typing indicators。
  • 跨机器远程 Mac 自动部署。

BuddySwitch 当前结合点

能力 现有入口 bridge 如何复用
创建外部 IM 身份 POST /api/im/connections 为每个 iMessage chat 创建或复用 external connection。
外部用户发给 actor POST /api/im/messages iMessage 入站消息转换成 BuddySwitch Central IM 消息。
actor 被唤醒处理 im.message.created wake 沿用现有 actor wake，不做 iMessage 专属 runtime。
actor 回复外部用户 message.send(reply_to=...) actor 不需要知道 iMessage，只回复 Central IM 消息。
外部侧读取回复 GET /api/im/events bridge 拉取 actor 回复并转发到 iMessage。

已验证的内部链路：external HTTP sender -> actor wake -> actor reply_to 回复 -> external event 可见一次。

关键风险与应对

风险 影响 应对策略
macOS 权限 imsg 无法读取 Messages 数据库或无法驱动 Messages.app。 启动前做 imsg chats、imsg rpc --help、发送 dry-run/探测；错误信息明确指向 Full Disk Access 与 Automation。
Messages / Apple Push 状态 手机消息没有同步到 Mac，bridge 没有入站事件。 健康检查区分 BuddySwitch 正常、imsg 正常、chat.db 没更新三类问题；提供人工修复步骤。
重复消息 / 回环 同一条 iMessage 被重复送入 BuddySwitch，或 bot 自己回复又被当作用户消息。 保存 rowid/guid cursor；忽略 is_from_me；BuddySwitch event cursor 只由 bridge 内部推进。
错误目标 actor 某个 iMessage chat 被投递给错误角色或实例。 显式 allowlist + chat 到 target_identity_id 静态绑定；不做 open DM。
隐私和权限面 运行 bridge 的进程可以访问 Messages 数据。 本地运行、最小配置、密钥文件 0600、日志默认不记录正文、只允许 allowlist chat。
功能期望外溢 群聊/附件/富交互会拉大复杂度。 MVP 明确只做一对一文本；真实使用稳定后再扩展。

验证策略

  • 先跑 BuddySwitch 现有 Central IM 测试，确认内部链路不坏。
  • bridge 单元测试：imsg message JSON -> BuddySwitch payload 映射、去重、忽略 self-message。
  • bridge 集成测试：mock imsg rpc + fake BuddySwitch IM API，覆盖入站和回复转发。
  • 真实 Mac 手工 smoke：从 iPhone 发一条 allowlist 消息，确认 actor 收到并回复回同一 iMessage chat。
  • 健康检查测试：缺少 imsg、缺少权限、actor 离线、BuddySwitch API 不可用时给出可操作错误。

当前状态

  • 可行性：外部实践和 BuddySwitch 内部接口都支持这个方向。
  • 代码结合：不需要改 Central IM 核心模型，bridge 可作为外部 IM 适配器接入。
  • 本机限制：当前本机未安装 imsg，所以还不能做真实 iMessage 收发验证。
  • 建议下一步：写正式实现计划，先做本地 bridge MVP 的最短闭环。
