Track Minimal Requirement Collaboration Model

结论：模型基本可行，但顺畅度取决于 read signal 和协作者书写纪律。

三个场景都能在目标 memo 的最小模型内完成闭环：owner 维护需求事实，协作者通过 material、update、proof、comment 推进事实和讨论，状态只保留 active、blocked、done。推演没有发现必须新增 workflow engine、owner decision queue、watcher、review 状态或 proof 覆盖矩阵的硬需求。

总体 verdict 基本可行但有摩擦
最强成立点 Owner facts 与 scattered communication 边界清楚
主要摩擦 Owner 阅读负担、proof 自描述、blocker 语义
不应新增 决策队列、review 状态、watcher、自动 done

场景 1: 多个 market actor 协作市场调研分析

Verdict: 基本可行但有摩擦

预设需求

Track 目标是收敛 BuddySwitch actor collaboration 的市场定位，产出可验证的市场分析 brief。非目标包括 campaign assets、最终 roadmap 和代码实现。

推演重点

研究材料会分散产生，竞品、ICP、定价结论会互相挑战。模型需要让协作者直接沟通，同时保证只有 owner 更新 requirement facts 和 done 判断。

Round 1
创建 / shaping

Owner 创建 active Track，写入 outcome、acceptance criteria、non-goals、now.next，再用 Track comment mention 各 market actor。评论只唤醒和分工，不修改需求事实。

Round 2
分散研究

ICP、competitor、pricing 分别追加 materials，PM synthesis 通过 reply/mention 追问反证和价值风险。Owner 不做消息路由，打开 Track 后阅读材料和近期评论。

Round 3
分歧 / blocker

定价 actor 报告“缺少定价锚点” blocker update，competitor 挑战 draft proof 引用不足。非 owner blocker 不自动改变 Track 状态；owner 可保持 active 并更新 now.next。

Round 4
验证 / done

PM synthesis 添加 final proof artifact，覆盖竞品引用、ICP 假设、支持/反证和定价风险。Owner 判断 proof 足够后设为 done，不要求所有讨论线程先 resolved。

顺畅点

  • Scattered mention/reply 适合市场分析师之间互相挑战证据。
  • Material 与 proof 的区别能容纳中间研究和最终 brief。
  • 三态足够表达 shaping、research、validation，不需要保存更多阶段。

摩擦点

  • 协作者加入依赖 owner 明确 mention，Track 创建本身不会唤醒参与者。
  • 多项研究型 acceptance criteria 需要 owner 手工核对。
  • 定价证据不足是局部风险还是全局 blocked，需要 owner 明确裁断。

场景 2: 多个 actor 协作开发 landing page

Verdict: 基本可行但有摩擦

预设需求

Track 目标是交付第一个可用 landing page draft。验收包括清晰 hero、problem/workflow/proof/CTA section、desktop/mobile proof 和 accessibility/smoke QA proof。

推演重点

文案、视觉、前端、测试高频互相影响。Track 负责共享需求和证据，实际开发执行仍应留在各 actor 私有 task 或工作流中。

Round 1
创建 / shaping

PM owner 建立 active Track，固定 page goal、验收和非目标，用 comment mention market、design、dev、test。没有新增任务分配表或 shaping 状态。

Round 2
并行贡献

Market 提交 copy material，design 提交视觉方向，dev 提交页面草稿 proof，test 提交 QA checklist。Actor 之间直接 reply/mention 对齐文案长度、布局和测试入口。

Round 3
交叉冲突

Design 认为 hero 抽象，test 指出 mobile proof 缺失，dev 报告“文案过长导致移动端折行/遮挡”。Owner 没有进入 review 状态，而是更新 now.next 收敛 hero 并补 mobile proof。

Round 4
验证 / done

Dev 和 test 补交 responsive、smoke、a11y proof。Owner 对照验收后设 done，未引入 backend、analytics、account、campaign automation。

顺畅点

  • 轻量跨职能协作可以用一个 Track 汇聚需求事实和证据。
  • Push signal 足够简单：mention/reply 唤醒具体 actor，proof/blocker 唤醒 owner。
  • Non-goals 对压住 analytics、CMS、完整网站 IA 很有效。

摩擦点

  • 多 actor 并行时 owner 必须认真读 track.open 摘要。
  • Proof 需要自然说明覆盖哪些 acceptance criteria，但系统不应生成覆盖矩阵。
  • 高频视觉、文案、QA 迭代中 scattered comments 会显得松散。

场景 3: 多个 actor 协作优化产品功能

Verdict: 基本可行但有摩擦

预设需求

优化 track.open read signals，让 actor 打开 Track 时能看到 state、now、materials、proofs、latest updates、recent comments、open threads、mentions to me、replies to me。

推演重点

该场景直接压力测试 memo 的 read signal 设计。目标是让 actor 知道下一步，不把 read signal 变成 owner decision queue 或 workflow state。

Round 1
创建 / shaping

Owner 写入 feature outcome、验收、非目标。Design/test 通过评论提问，评论是输入而不是事实变更。显式 mention 足够，不需要 participant/watch list。

Round 2
协作展开

Design 加输出形状 material，dev 加实现 update，test 加测试材料，market 加用户语境材料。Owner 读完共享事实后更新 now.next。

Round 3
实现歧义

Dev 发现 actor-relative reply 语义不清，test 报 blocker update，market 挑战 proof 范围。Blocker report 是 signal；只有 owner 接受后才进入 state=blocked 和 now.blocker。

Round 4
验证 / done

Owner 打开 Track，看到 read signal 的完整投影，判断 proofs 满足 actor-relative comments、open threads、proof/blocker cues 和 focused tests 后设 done。

顺畅点

  • 模型适合围绕一个产品功能聚合设计、实现、测试和市场反馈。
  • track.open 作为 read signal 入口是正确方向。
  • Proof/blocker 保持为证据和信号，避免状态膨胀。

摩擦点

  • mentions_to_me 与 replies_to_me 必须绑定完整 actor address，不能只按 role 或 actor id 粗略匹配。
  • open_comment_threads 只返回 count 不够，需要可操作摘要。
  • Proof 添加后 owner 需要被提醒；若 push 还未完整实现，read signal 至少要明确承接。

横向发现

三轮 sub-agent 推演在不同场景下反复撞到相同边界，说明问题不是某个场景特例。

Repeated across scenarios
模型最稳定的部分：owner facts 与 collaborator inputs 分离。 协作者可以强力影响 requirement，但不能静默修改 outcome、acceptance、non-goals、state 或 done 判断。这个边界在三类场景中都成立。
Scattered comments 足够替代 owner 路由。 Actor 之间直接 mention/reply 能解决大部分横向对齐问题。新增 watcher、subscriber、全员广播或 participant list 在三类场景里都不是硬需求。
最大的顺畅度瓶颈是 track.open 的 read signal 质量。 如果只给 count、id 和原始列表，owner 与协作者会频繁二次查询。需要紧凑摘要，但不能升级为 decision queue。
Proof 需要自描述，但系统不应内建覆盖矩阵。 三类场景都需要 proof 自然说明它覆盖哪些验收点。自动 coverage matrix 会把 Track 推向 workflow/approval system，不符合目标 memo。
Blocker report 与 Track blocked 必须被清楚区分。 任何 actor 都可以报告 blocker，但只有 owner 接受后 Track 才进入 blocked，并且必须有 now.blocker。
不要复活 owner decision queue。 推演中多次出现“owner 需要看什么”的压力，但可用 read signal 和 owner 判断解决。把 cue 持久化成 queue 会违背目标 memo 的禁止项。

建议

建议保持模型小，但给出使用约定和 read signal 细节，避免用新状态或新系统解决书写和展示问题。

Keep model minimal

1. 补一段协作者邀请约定

Owner 邀请协作者参与 Track 的默认方式是添加 Track comment 并 mention 具体 actor。不要新增 participant、watcher 或 subscriber 字段。

2. 补 proof 写法约定

Proof 文本应自然列出覆盖的 acceptance criteria、剩余风险和证据引用。系统只展示 proof，不生成 proof-to-acceptance coverage matrix。

3. 补 blocker 文案边界

Update 可以写“某 actor 报告 blocker”，但 UI/输出必须区分它与 owner-accepted state=blocked。

4. 细化 actor-relative comments

mentions_to_me 和 replies_to_me 使用完整 {actor_id, role_id} 匹配，并返回 comment id、thread id、作者、时间、状态和短 preview。

5. 让 open threads 可操作

open_comment_threads 不只返回数量，至少返回 thread id、最新评论、评论数、是否包含对当前 actor 的 mention/reply。

6. 保留禁止项

继续禁止 review、approved、waiting_owner、needs_owner_decision、自动 done、强制 comment resolution、watcher/broadcast、generic state machine。

评测结论 目标 memo 的方向可以继续推进。它不需要变大，但需要把“怎样写 proof、怎样报告 blocker、怎样通过 comment 邀请协作者、track.open 应展示什么粒度”说得更具体。
