# BuddySwitch 开发宪法 v1

> 本文档用于约束 BuddySwitch 项目的产品迭代、架构演进与 coding agent 执行风格。它不是讨论稿，而是默认执行准则。除非有更高优先级的明确指令，否则本文件应被视为仓库级行为约束。

## 1. 北极星

BuddySwitch 当前阶段的唯一目标，不是“做得全面”，也不是“做得优雅到未来十年都不用改”，而是：

**以最清晰、最直接、最可验证的方式，持续推进产品核心能力。**

本项目当前采用以下优先级顺序：

1. **效果提升**：是否更接近真正解决核心问题。
2. **迭代效率**：是否更快得到真实反馈、真实结果、真实可运行产物。
3. **架构清晰**：是否让系统更容易理解、修改、替换、删除。
4. **实现成本**：当前阶段不是优先决策因子。

当前阶段，**不要为了节省 token、模型成本、基础设施成本而牺牲效果与迭代速度**。只有当成本本身成为明确瓶颈时，才进入优化范围。

---

## 2. 总纲：前进式迭代

BuddySwitch 采取**前进式迭代**，而不是“包袱式演进”。

所谓前进式迭代，指的是：

- 默认认为旧设计可以被替换，而不是必须长期兼容。
- 默认认为今天的最佳解只服务于当前最重要的问题，而不是预支未来五层抽象。
- 默认认为一次迭代应该收敛到一个核心矛盾，而不是同时修十个方向。
- 默认认为代码、文档、技能、提示词都可以被重写，只要能让系统更简洁、更强、更容易继续前进。

**能直切，就不要绕。能替换，就不要叠加。能删除，就不要保留。**

## 3. 非协商原则

以下原则默认对所有人类开发者、AI coding agent、技能工作流、自动化流程生效。

### 3.1 聚焦一个核心问题

每一轮开发必须能明确回答：

- 这轮要解决的核心问题是什么？
- 为什么它是当前最重要的问题？
- 解决它之后，系统会获得什么可验证提升？

如果一个改动无法直接服务当前核心问题，默认不做。

禁止：

- 顺手做一堆“以后可能有用”的改进。
- 在主要问题尚未打通前，横向扩展到多个次要方向。
- 用“先搭好通用框架以后会方便”作为默认理由。

### 3.2 问题一旦收敛，就停止发散

当问题已经被定义清楚，接下来应进入攻坚，而不是继续发散讨论。

禁止：

- 已经确定优化目标后，仍不断引入新的可能性分支。
- 一边做实现，一边把任务扩展成更大的系统设计。
- 因为模型“想到更多点子”而偏离当前任务闭环。

### 3.3 先打通闭环，再追求完整

所有开发优先级都服从“闭环优先”。

优先做：

- 能跑通的最短主路径。
- 能验证价值的最小系统。
- 能支撑下一轮判断的真实产物。

延后做：

- 完整配置体系。
- 漂亮但非必要的抽象层。
- 泛化能力尚无第二真实场景支撑的设计。
- “为未来可能扩展”而预留的大型接口。

### 3.4 简单优先于优雅，清晰优先于聪明

BuddySwitch 不追求炫技式工程，不奖励聪明但难懂的设计。

优先选择：

- 更短路径。
- 更少概念。
- 更少隐式行为。
- 更少跨层跳转。
- 更容易让新 agent 或新开发者读懂的结构。

如果一个方案“理论上更优雅”，但会引入更多层次、更多状态、更多命名、更多间接性，默认不选。

### 3.5 禁止投机性设计

没有真实需求，不要预建能力。

禁止默认引入：

- 插件系统
- 规则引擎
- 工作流引擎
- 事件总线
- 过早服务化 / 微服务化
- 通用规则语言
- 多租户复杂隔离层
- 大而全权限模型
- 提前版本化的内部接口
- 为“未来多产品线”准备的大型抽象基座

**出现第二个真实、持续、明确的使用场景之前，不做通用化。**

### 3.6 单体优先，模块清晰，边界晚一点再拆

在尚未被真实复杂度逼迫之前，优先保持：

- 单体或近单体架构
- 明确目录边界
- 清晰模块职责
- 尽量少的运行时分布式复杂性

先把模块边界做对，再讨论服务边界。

### 3.7 重构优先于兼容包袱

当旧实现阻碍继续迭代时，优先考虑：

- 直接重构
- 直接替换
- 直接删除

而不是：

- 再包一层兼容层
- 再加一层 adapter
- 同时维护新旧双轨很久
- 用大量 feature flag、双写、兼容开关长期拖着

### 3.8 兼容性不是默认美德，而是有成本的例外

默认不为历史兼容付费。

只有满足以下条件之一，才应保留兼容性：

- 已有真实线上用户或外部调用方正在依赖。
- 已有不可逆数据必须安全迁移。
- 存在明确的回滚窗口需求。
- 用户已明确要求保持兼容。

除上述情况外，**破旧立新优于兼容叠层**。

### 3.9 删除是正式手段，不是失败

在 BuddySwitch，删除代码、删除文档、删除冗余抽象、删除过期技能，都是积极行为。

当某个东西已经：

- 不再承载当前主路径
- 只增加理解负担
- 只是为了“也许以后还会用”而保留
- 被新实现完整替代

就应该删除，而不是收藏。

## 4. Coding Agent 执行协议

所有 coding agent 在 BuddySwitch 中执行任务时，默认遵循以下协议。

### 4.1 非 trivial 任务：先探索，再规划，再实现，再验证

对于多文件改动、架构调整、未知代码区、复杂修复，必须先：

1. 探索当前实现与上下文。
2. 形成最小充分计划。
3. 再进入编码。
4. 最后用明确验证手段确认结果。

禁止直接“看到需求就开写”，除非任务足够小，小到可以一句话描述差异且几乎无歧义。

### 4.2 每次执行都要先找当前瓶颈

agent 不应平均用力。

每轮执行前，应先判断当前最大瓶颈属于哪一类：

- 需求不清
- 主路径未打通
- 架构阻碍变更
- 测试 / 验证不足
- 代码可读性过差
- 技术债已开始拖慢速度
- 外部依赖或环境阻塞

然后集中解决最阻碍前进的那个点。

### 4.3 默认自主解决局部歧义

如果歧义不会改变产品本质、不会造成严重返工、不会影响外部契约，agent 应基于上下文自行做合理决定并推进，而不是频繁停下来请求确认。

只有涉及以下事项时，才值得中断确认：

- 产品语义发生明显变化
- 数据模型将不可逆改变
- 外部接口 / 用户承诺将被破坏
- 安全、权限、支付、隐私等高风险问题

### 4.4 输出必须面向执行，而不是面向表演

agent 的中间产物与最终总结必须帮助下一步行动，不应堆砌空泛表述。

优先输出：

- 当前判断的核心问题
- 采取的方案
- 具体改动点
- 如何验证
- 剩余风险
- 下一步建议

避免输出：

- 大量泛泛方法论
- 与当前任务无关的发散建议
- 看似完整但不能指导行动的长篇分析

### 4.5 改一次就验证一次

只要条件允许，agent 每做完一个有意义的改动块，就应进行验证，而不是积累大量改动后一次性赌结果。

验证可包括：

- 单元测试
- 集成测试
- lint / build
- 手动运行主路径
- 截图对比
- 关键日志检查
- 核心命令行输出检查

### 4.6 优先根因修复，禁止表面压制

面对报错、失败、性能问题、结构混乱时，优先解决根因。

禁止：

- 用 suppress / ignore 掩盖真实错误。
- 用额外条件分支逃避理解问题。
- 用兜底逻辑长期遮盖坏状态。
- 在不知道为什么的情况下“改到不报错为止”。

### 4.7 复杂任务必须可续跑

当任务较长、跨度较大、可能跨多次会话执行时，必须形成可续跑文档。该文档应让新 agent 或断点恢复后的 agent 能继续推进，而不是依赖隐性上下文记忆。

## 5. 架构原则

### 5.1 架构服务于当前瓶颈，而不是抽象欲望

所有架构决策都必须回答：

- 这个结构具体解决了什么当前问题？
- 如果不这么做，当前迭代会卡在哪里？
- 这个结构是否在降低后续修改成本？

如果回答不具体，说明设计过度。

### 5.2 模块职责要硬，层次数量要少

好架构不是层越多越专业，而是：

- 每层职责明确
- 跨层关系清楚
- 调用路径短
- 状态变化容易追踪

优先减少：

- 中间层
- 包装层
- 重复 DTO
- 形式大于内容的 interface
- 只为了“看起来解耦”而存在的空抽象

### 5.3 第二次真实复用之前，不做大抽象

第一次出现需求时，优先做具体实现。

只有当相同模式被第二次、第三次真实重复验证后，才允许上提抽象。

换言之：

- 先复制少量清晰代码，不急着抽象。
- 当重复已经明确、稳定、可命名，再收敛成共享结构。

### 5.4 先可改，再可扩，再可配

结构演进顺序默认是：

1. 可理解
2. 可修改
3. 可验证
4. 可扩展
5. 可配置
6. 可平台化

不要跳级。

### 5.5 运行时复杂度比代码行数更昂贵

BuddySwitch 更警惕的是：

- 分布式状态
- 隐式异步耦合
- 多入口真相源
- 多份配置漂移
- 双轨逻辑长期并存

为了避免这些问题，允许局部代码显得“笨一点”，但整体必须更可控。

## 6. 文档、指令与知识组织原则

### 6.1 根文档必须短、硬、准

仓库根部给 agent 的总指令文档，必须：

- 短
- 准
- 可执行
- 少空话

不要把根文档写成冗长百科。根文档应该只承载：

- 项目目标
- 非协商规则
- 运行 / 测试 / 验证方式
- 关键目录说明
- done 的定义
- 禁做事项

### 6.2 高频重复工作，沉淀为 skill

当某类任务反复出现，并且有相对固定的判断流程、步骤、输入输出格式时，应将其沉淀为 skill，而不是长期塞在根文档或靠人每次重写 prompt。

skill 应只解决单一清晰问题，边界明确，不要做万能技能。

### 6.3 复杂特性或大改动，沉淀为执行计划文档

复杂特性、跨模块重构、存在重要未知数的任务，应使用可续跑的执行计划文档。

该文档必须能回答：

- 要达成什么用户可见结果
- 当前状态是什么
- 计划怎么做
- 已完成到哪里
- 发现了什么问题
- 为什么做过某些决策
- 如何验证结果

### 6.4 只记录关键决策，不记录流水账

不是所有事情都值得写文档。

只有以下内容值得长期保留：

- 重要架构决策
- 关键取舍原因
- 会影响后续大量工作的边界定义
- 会被新成员反复问到的运行方式与规则

普通探索废话、过时计划、被推翻的想法，不应长期堆在主文档里。

## 7. 变更策略

### 7.1 小批量提交

更小的改动，更容易：

- 审阅
- 回滚
- 定位问题
- 快速合并
- 减少上下文遗失

默认偏好短生命周期分支 / worktree、小批量改动、尽早集成。

### 7.2 一次改动只承载一个主意图

一个 PR、一个变更集、一个 agent 任务，默认应尽量只有一个主意图。

禁止在同一变更里混入：

- 功能实现
- 大规模重命名
- 风格清洗
- 顺手重构
- 无关目录整理

除非这些内容是不可分割的。

### 7.3 先合主路径，再做周边优化

只要核心主路径还不稳定，就不要投入太多时间做边缘优雅化。

例如：

- 主链路未通，不优化二级体验。
- 主逻辑未稳，不做大量配置抽象。
- 业务未成立，不做平台化。

## 8. 验证与质量原则

### 8.1 没有验证，就不算完成

BuddySwitch 的 done 不是“代码写了”，而是“结果被验证了”。

每个任务至少应具备以下之一：

- 自动化测试通过
- 主路径手动跑通
- UI 前后对比明确
- 命令输出符合预期
- 日志 / 状态 / 数据变化可证明

### 8.2 质量门槛要自动化，少靠口头提醒

能够机器判断的规则，尽量交给自动化。

例如：

- lint
- test
- 类型检查
- 安全扫描
- 禁止修改某些敏感目录
- 必须补充某类验证

口头约定可以帮助方向一致，但真正能稳定执行的是自动门槛。

### 8.3 架构目标必须被度量

如果一个架构目标很重要，就不要只写在嘴上。

应尽量将其转化为可验证约束，例如：

- 主路径必须有测试覆盖
- 不允许明文 secrets
- 核心模块依赖方向不能反转
- 某些目录的改动必须通过特定检查
- 核心接口响应时间不能超过某阈值

不能被验证的“原则”，很容易在高压迭代中失效。

## 9. 允许的探索，禁止的漂移

BuddySwitch 允许探索，但探索必须有边界。

### 9.1 允许的探索

允许：

- 为重大未知数做快速 spike / 原型
- 为架构方向做小规模可抛弃验证
- 为高风险实现先做试验性分支

但要求：

- 时间盒明确
- 产出结论明确
- 试验代码默认可删除
- 不允许试验代码半成品长期混入主路径

### 9.2 禁止的漂移

禁止：

- 从一个具体任务滑向平台化设计
- 从一个 bug 修复滑向全面重构
- 从一个 skill 扩成万能系统
- 在没有真实验证前，因想象中的未来需求不断加层

## 10. Anti-Patterns 黑名单

以下行为在 BuddySwitch 中默认视为反模式：

1. 为了显得专业而增加层次。
2. 为未来用户写今天没人需要的系统。
3. 因舍不得删而长期保留旧逻辑。
4. 在没有第二场景前提前抽象。
5. 把“灵活性”建立在复杂配置和隐式行为上。
6. 为了避免决定而引入通用框架。
7. 用兼容层掩盖应该重构的问题。
8. 用大 PR / 大任务吞掉多个独立问题。
9. 没有验证就宣布完成。
10. 已经收敛问题后继续发散。
11. 用模型生成速度掩盖思考不清。
12. 把文档写成长篇口号，而不是可执行约束。

## 11. BuddySwitch 的默认工作流

### 小任务

如果任务范围清晰、改动很小、风险很低：

- 直接实现
- 立即验证
- 输出结论与改动点

### 中任务

如果任务涉及多文件、已有逻辑理解、结构调整：

- 先探索
- 再写简短计划
- 实现
- 验证
- 总结剩余风险

### 大任务

如果任务跨模块、存在未知依赖、可能持续多轮：

- 建立执行计划文档
- 分阶段推进
- 每阶段更新进度、发现、决策
- 每阶段都要有可见结果
- 直到闭环完成

## 12. Done 的定义

一个任务只有在满足以下条件时，才算真正完成：

1. 当前核心问题已被实质推进，而不是只做了外围动作。
2. 改动范围与任务目标一致，没有明显无关扩张。
3. 结果已通过适当方式验证。
4. 代码与结构比改动前更清晰，至少没有更乱。
5. 若产生了新的长期约束，已写入相应文档或技能。
6. 若旧实现已被替代，冗余部分已删除或明确列入下一步删除计划。

## 13. 对未来 Buddy / Skill 体系的附加原则

BuddySwitch 本质上会沉淀大量面向 agent 的工作方式，因此特别强调：

- **Buddy 是 skill collection，不是杂物间。**
- **Skill 是窄边界、强触发条件、强操作性的工作单元。**
- **总指令保持克制，把专业流程下沉到 skill。**
- **重复踩坑后再加规则，不靠一开始写满所有可能。**
- **能通过 hook 或自动检查强制的，不靠 agent “记得”。**

## 14. 一句话版本

如果必须把这份宪法压缩成一句话，那就是：

**围绕当前核心问题，小步快跑，直切闭环；默认不背历史包袱，不做未来主义抽象，不搞花哨复杂度；一切以清晰、可验证、可继续前进为准。**
